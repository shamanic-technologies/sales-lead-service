# Project: lead-service

**The GitHub repo is `sales-lead-service`; the Hetzner box clones it as `/root/distribute/repos/lead-service`** (and the container is `distribute-lead-service-1`, the env file `env/lead-service.env`). A post-deploy poll built on the repo name reads a path that does not exist, which looks exactly like a deploy that has not landed — cost a 10-minute exhausted poll on v0.65.1 while `deploy.log` already said `lead-service: healthy on 28307cd1`.

## CI never touches a database the service uses

- **`.github/workflows/ci.yml` provisions its own `postgres:17` service container and points `LEAD_SERVICE_DATABASE_URL` at it — `secrets.LEAD_SERVICE_DATABASE_URL` must not appear in that file, on any event.** It used to: the migration step ran against the single live DSN on `pull_request`, so merely OPENING a PR moved the production schema before review, before merge, and before the code expecting the new shape shipped — and a PR later closed or reworked left its migration applied with nothing using it (#397). Production migrations come from `migrate()` on boot in `src/index.ts`, not from CI. `tests/unit/ci-workflow.test.ts` fails the build if any `${{ secrets.* }}` reference returns.
- **The CI database is EMPTY.** Anything under `tests/integration` must seed its own rows; do not write a test that passes only because production data happens to exist (that is how brand-service's suite came to fail on a clean database — brand-service#385/#387). A throwaway service container was deliberately preferred over the ephemeral Neon branch the fleet used at the time: a Neon branch was cut from the default branch, so it arrived carrying production data, and it leaked compute hours when a run failed. Neon has since been deleted and every database is one Postgres container on the Hetzner box — so there is no branch-per-CI-run option to reach for, and the rule that stands is the one above it: CI provisions its own empty `postgres:17` and never points at a database the service uses.

## The sync back into `staging` is a MERGE commit, never a squash

A hotfix goes to `main` and is then synced back into `staging` by a PR whose head IS `main` (`chore: sync vX to staging`). Merge it with `--merge`. Squashing it (`gh pr merge --auto --squash`, which is the right default for every OTHER PR here and therefore the reflex) writes a NEW commit onto staging carrying content that already exists on main under a different sha, so the two branches stop sharing history for those files. Nothing looks wrong: the sync PR merges, staging's tree is correct, and CI is green. The next sync is the one that pays — it conflicts on files whose content is byte-identical on both sides, which reads as a real divergence and invites resolving hunks by hand in a tree that needs no resolution at all.

Recovery, if it has already happened: branch off `origin/staging`, `git merge origin/main`, resolve EVERY hunk to main's version, and confirm with `git diff origin/main --stat` coming back empty before pushing — main is the source of truth and staging is a buffer that deploys nowhere, so any hunk where staging wins is a mistake. (2026-09-17, #540 squashed → #542 DIRTY → #543.)

## Migrations — hand-author, do NOT `db:generate`

The drizzle meta snapshots (`drizzle/meta/*_snapshot.json`) stop at `0007`; migrations `0008`+ were all hand-authored. So `npm run db:generate` (`drizzle-kit generate`) has no recent snapshot to diff against and drops into an interactive prompt asking to **recreate every table** — it cannot produce a clean incremental migration. Convention: **hand-author the `.sql` file + add the journal entry to `drizzle/meta/_journal.json` yourself**. Make every statement idempotent (`DROP COLUMN IF EXISTS`, `DROP INDEX IF EXISTS`, `CREATE INDEX IF NOT EXISTS`, or `DO $$ … IF EXISTS … $$`) — see `0022`/`0023` as templates. `npm run db:migrate` (`drizzle-kit migrate`) applies the journal's `.sql` files and does NOT need the snapshots, so this works at boot.

- `src/lib/email-gateway-client.ts` — Email-gateway POST /status client for delivery checks
- `src/lib/leads-registry.ts` — Global lead identity registry (leads + leadEmails tables)
- `src/lib/people-client.ts` — human-service people gateway client (provider-agnostic search/enrich via apollo OR apify; lead-service no longer calls apollo/apify directly). **Do NOT branch on provider in the consumer** (`if (provider === "apollo")`). The gateway is provider-agnostic: pass every identity field you stored (`providerPersonId` from the apollo-specific column when present, `firstName`/`lastName`/`domain` when present) and let the gateway pick the reveal path. The `(provider, providerPersonId)` pair is what disambiguates the id — `provider` qualifies it, so a generic wire field is correct; don't push per-provider routing back into lead-service. (Set 2026-06-14, v0.21.2 apollo reveal-by-person-id regression fix.)
- `src/lib/{campaign,brand}-client.ts` — campaign/brand detail fetches for search context; `src/lib/runs-client.ts` — runs-service distributed tracing. **Per-brand configuration is the data of an (org, brand) PAIR, so `orgId` is a REQUIRED argument on every `brand-client` read and `x-org-id` always goes on the wire.** A brand row is a shared global identity: any org claiming the same domain gets the same brand id, and two such orgs legitimately optimize for different goals. brand-service answers a brand claimed by exactly one org either way, but refuses to guess for a brand claimed by several — so an org-less read fails there (lead-finding stops) rather than leaking a neighbour's configuration. `buildHeaders` throws before any fetch when the org is blank; do NOT make it optional again, and do NOT substitute a plausible stand-in org, which is the leak being closed. Every call site is an org-scoped `requireOrgId` handler, so the org is always in hand.
- `src/db/schema.ts` — Drizzle ORM table definitions (PostgreSQL); `src/db/index.ts` — connection; `src/config.ts` — env config; `src/instrument.ts` — Sentry
- `tests/` — Test files (`*.test.ts`)
- `openapi.json` — Auto-generated from Zod schemas, do NOT edit manually

## Data Layering

- lead-service owns silver lead entities (`leads`, `lead_contact_methods`, `leads_organizations`, `organizations`) and per-campaign lifecycle rows (`leads_campaigns`).
- `GET /orgs/leads?view=basic` is a Gold serving projection for dashboard list views: return only the locked slim lead shape, current-employer org summary, primary email, lifecycle fields, and live delivery overlay.
- Prefer a Gold view/projection before a Gold table. Materialize only after profiling proves the joins themselves are the bottleneck; do not materialize live delivery status, and do not bake the known multi-`current=true` employment defect into stored Gold state.
- For current employer reads, never trust a bare `current=true` filter alone. Use deterministic winner selection: enriched org first, newest employment row next, stable organization id last.
- `GET /orgs/leads` brand/org scope must be ONE row per PERSON, not per campaign-membership. `leads_campaigns` is membership-grain (one row per person × campaign/serve), so brand/org reads collapse to one row per `lead_id` via global `DISTINCT ON (lead_id)` (winner = most-advanced lifecycle `served>claimed>buffered>skipped`, then latest `served_at`/`created_at`/`id`) — the kept row fires the email-keyed delivery overlay and carries the person's full engagement. Both paths dedupe: slim (`basicLeadQuery`) + full (`fetchLeadCampaignChunk`), sharing `src/lib/lead-list-query.ts`. Campaign scope (`campaignId` present) stays flat — never collapse it. The dedup is GLOBAL (a subquery), keyset-paginated over the deduped relation; never `DISTINCT ON` inside a keyset chunk (splits a person across chunk boundaries). (#320.)
- **Each lead carries its ACTIVE audience for the brand — resolved server-side, never via a client-side list fan-out.** `GET /orgs/leads` (both `view=basic` and full) returns `audience: { id, name, avatarUrl } | null` per lead. lead-service owns `leads_campaigns.audience_id` on only ~5% of rows; the rest resolve by EMAIL → active-audience membership. Both keys (tagged `audienceId` + `email`) are forwarded per chunk to human-service `POST /internal/audiences/resolve` (server-to-server, direct to `HUMAN_SERVICE_URL`, NOT the api gateway → no 100KB body cap: the resolver mounts its own 25MB parser before human-service's global 100KB `express.json()`). Request `{ orgId, brandId, audienceIds[], emails[] }` (deduped per brand group); response `{ byAudienceId, byEmail }` maps, correlated back per lead (tagged audience card preferred over email membership). human-service owns the brand-correct pick. Grouped by the scoped `brandId` when present, else the row's primary brand. Resolution runs BEFORE each chunk is written, so a resolver failure fails loud (clean 500 pre-stream / destroyed socket mid-stream) — never a silently-blank `-`. Do NOT re-introduce a browser-side membership fan-out (that 413'd the gateway — the reported bug). Client: `src/lib/audience-client.ts`. (#346, human-service#166.)
- **Timestamps read via raw `sql` come back as `Date` OR `string` — NEVER call `.toISOString()` on them directly; normalize via `toIsoTimestamp` (`src/lib/basic-leads.ts`).** postgres.js (`prepare:false`) hands a timestamptz column back as a `Date` on some paths and a raw string on others; a bare `row.servedAt.toISOString()` throws `is not a function` the moment it's a string, and on a streaming response (headers already sent) that throw destroys the socket → callers see `UND_ERR_SOCKET`, not a clean 500. Both `/orgs/leads` paths must share the helper: type raw rows `Date | string | null`, normalize at map time. The slim path (`basic-leads.ts`) always did; the full path (`fetchLeadCampaignChunk`) diverged and crashed (#328, v0.31.1). When adding any new timestamp field to a raw-`sql` query, route it through `toIsoTimestamp`, not `.toISOString()`. (#328.)
- **WRITE-side dual of the above — NEVER bind a raw JS `Date` into a raw `db.execute(sql\`...\`)` template; bind `date.toISOString()`.** A raw `sql` template passes params straight to postgres.js `Bind`, which (unlike drizzle's typed insert builder `db.insert().values({ col: new Date() })`, or postgres.js's own tagged template) does NOT serialize a `Date` — it calls `Buffer.byteLength(value)` and throws `TypeError [ERR_INVALID_ARG_TYPE]: The "string" argument must be of type string ... Received an instance of Date` at Bind time. This is a CLIENT-side throw, so it is invisible to raw-SQL / `EXECUTE ... USING` tests run directly against the DB (the query text is fine; the driver never gets to send it) — the DB looks fully healthy while every request 500s. The ISO string casts to the timestamptz column. This 500'd EVERY `POST /public/conversions` conversion event since the beta ingest — `conversion_events` had 0 real rows for weeks (only `ping`, which uses SQL `now()` with no Date param, worked). When writing via raw `db.execute(sql\`...\`)`, bind primitives only (string/number/null/`.toISOString()`); reach for `db.insert()`/`db.update()` typed builders if you want a `Date` serialized for you. (#357/#370, v0.39.0.)
- **A person is ONE identity, keyed EMAIL-FIRST — never serve a lead whose email is not registered.** `idx_lcm_channel_value` makes "one email = one lead" a hard invariant, and the read path keys the email-gateway delivery overlay on the lead's REGISTERED email. So a served lead with no email contact method can NEVER resolve contacted/sent/delivered: it is invisible in the dashboard funnel, absent from outreach counts, and absent from features-service conversion attribution — paid-for emails missing from every cost-per-outcome denominator. `upsertLeadFromPerson` therefore resolves identity as (1) the lead that already owns `person.email`, (2) the lead carrying `person.providerPersonId`, (3) a fresh row — email BEFORE provider id, because provider ids churn (a re-crawl mints a new id for the same human) while a registered email cannot move. `registerServedEmail` then guarantees the returned lead owns the email (re-resolving on the concurrent-serve race) and fails loud if it can't — do NOT restore the old warn-and-serve-anyway branch, do NOT weaken the global uniqueness, and do NOT make the read path fall back to `leads.metadata->>'email'` (that hides an absent record and leaves every other consumer wrong). Historical rows repaired by `scripts/repair-served-lead-emails.ts` (dry-runnable, idempotent, `leads_campaigns.repointed_from_lead_id` records the pre-repair attribution). (#393.)
- **A serve that was paid for and never contacted is un-consumed by ARCHIVING the `leads_campaigns` row into `requeued_serves` and DELETING it — never by flipping its status.** `idx_lc_lead_campaign` is unique on `(lead_id, campaign_id)` regardless of status, so a surviving row of ANY status makes the serve path's `ON CONFLICT DO NOTHING` keep the stale row (old run ids, old `served_at`) if the person is re-served to the campaign that lost them: the re-serve is mis-attributed and the person reads as long-since contacted while the vendor has just received them. `scripts/requeue-uncontacted-serves.ts` (one-time, `--dry-run`, idempotent, reversible from `row_snapshot`, tagged `reason`) is the only writer; the serve path never touches that table. Contact evidence is NEVER inferred from "the send failed": it comes from the service that submitted to the vendor, in two fail-closed gates — `scripts/sql/exclude-vendor-contacted.sql` drops anyone holding an `instantly_campaigns` row (cross-brand/cross-org, deliberately conservative, in SQL because only instantly-service's own DB can answer it), then the script asks email-gateway `POST /orgs/status` at BRAND scope for the per-brand answer. **The no-re-serve guarantee itself is human-service's `brand_suppressions` (keyed `(org, brand, email_norm)`, 3-month window) — lead-service does not own it and must not write it; this repair only makes the lifecycle row correct so a released person can be re-served.** Do NOT generalise any of this into a recurring sweep, retry loop, or detector: the producer bug (instantly-service#570/#573) is fixed and the affected set is closed. (#406.)
- **A lead's `timezone` comes out of the stored enrichment or it stays NULL — never from a country, a city, or any other heuristic.** Apollo returns `time_zone` on the ENRICHMENT response only (never on search) and has since February 2026; the reader that persists it landed in August, so 86,738 leads carried a null timezone and were refused at the send step after we had already paid to find, enrich and write to them. `scripts/backfill-lead-timezone.ts` (one-time, `--dry-run`, idempotent via `timezone IS NULL`, reversible from the `--report` id list) fills them from `scripts/sql/apollo-lead-timezones.sql`, a plain SELECT against apollo-service's own `apollo_people_enrichments`. **That SQL step is what makes the repair provably credit-free**: apollo-service `POST /enrich` BUYS on a cache miss, and its cache hit additionally requires `email IS NOT NULL AND email_status = 'verified' AND created_at > 12 months ago`, so driving 28k rows through it would have re-purchased everyone those predicates exclude — the value is already stored, so it is read, not re-bought. The query must read `COALESCE(time_zone, response_raw->>'time_zone')`: apollo-service promotes the typed column only for enrichments written after its own reader landed (43,966 raw vs 17,317 typed in prod), and the typed column alone recovers ~17k people instead of ~28k. A lead with no city and no country (55,349 of them) keeps a null timezone — that is the honest answer and the send chain accepts it. **Match a large caller-supplied key set with `col = ANY(${ids}::text[])`, never by joining against `unnest(...)`**: Postgres hashes the array once and probes it per row, while the join/`EXISTS` form plans as a nested loop over a function scan — 86,738 leads × 41,761 known people, which never returned (the same count comes back in under a second as an array probe). Wrap it in `coalesce(..., false)` when the column is nullable, because the comparison is NULL for those rows and a NULL drops them out of BOTH the matched bucket and its complement. Do NOT generalise this into a recurring sweep: the live path persists the timezone at serve, and the affected set is closed. (#428.)
- **A campaign-scoped read answers for the campaign IDENTITY, not the single stored campaign row.** A campaign as the customer knows it is `(org, brand, sales funnel, acquisition channel)` — campaign-service's own key (its migration 0044 `uniq_campaigns_org_brand_funnel_channel`). campaign-service used to mint a NEW row on every workflow switch, so one real campaign exists in storage as dozens of rows, one alive and the rest stopped; product surfaces show one line per identity, and features-service already totals that way. So `GET /orgs/leads?campaignId=` and `GET /orgs/stats?campaignId=` resolve the family first (`src/lib/campaign-identity.ts` — the same grouping features-service uses — via `resolveCampaignFamily`, an ORG-scoped read of campaign-service `/campaigns`) and filter on `campaign_id = ANY(family)`. Three consequences that are load-bearing, not incidental: (1) a MULTI-member scope dedupes to one row per person exactly like brand scope, else a campaign count exceeds the brand count for the same people; (2) delivery evidence is keyed by email-gateway on the campaign that SENT, so a multi-member scope asks in BRAND mode and reads the identity's members out of `byCampaign` (`flattenFamilyStatus`) — asking in campaign mode for the live id alone reports a paid-for, contacted person as never contacted, which is the same bug in the other direction; (3) the read is ORG-scoped because campaign-service's `brandId` filter matches the legacy `brand_ids` ARRAY, and a member carrying the brand only in `brand_id` would drop out — a PARTIAL family is worse than not widening. Resolution failing falls back to the single requested row with a loud log, never to a partial family and never to the brand. Never rewrite, repoint or delete stored rows to "fix" this: every campaign id keeps answering, only what a campaign-scoped read TOTALS changed. Do NOT add a query param for callers to opt in — the existing scope means the identity. (#410.)
- **`GET /orgs/leads` answers for the ACTIONABLE population by default — `buffered,claimed,served`, NOT `skipped` — and a caller widens it with `?status=`.** The delivery overlay is only fetched for `status = 'served'` rows, so a `skipped` row carries no engagement evidence by construction: every one of its status fields is false/null, no engagement-bucketed view can reach it (the dashboard's tabs are all engagement steps), and features-service's revenue engine drops it (it keeps only persons with EV > 0 or a delivery milestone). For one real brand it was 53,760 of 53,777 rows — ~82% of a 102 MB slim body, on an endpoint the dashboard polls every 30s. `status` takes a comma-separated list of the four lifecycle statuses or `all`; an unknown value is a 400, never a silent fallback (`parseLeadStatusFilter`, `src/lib/lead-list-query.ts`). The predicate is applied INSIDE the dedup subquery as well as on the outer query, so the winning membership row per person is chosen among the statuses the caller asked for. Do NOT re-widen the default to "everything" to fix a consumer that lost rows — teach that consumer to ask (the admin app asks for `all`, which is why it still has a Skipped tab). Narrowing by lifecycle is a different lever from bounding how much comes back — see the next bullet. (#414.)
- **`GET /orgs/leads` honours a caller-supplied `limit`, and no `limit` still means the WHOLE population.** The bound is expressed as `limit` + an opaque `cursor` (its positional twin `offset` is accepted for the gateway's published contract), and the response carries `nextCursor`: the position to resume from, or null when the response reached the end. The walk is keyset over `(created_at, id)` — `id` is unique, so that order is TOTAL and a walk visits every row exactly once, no gaps, no repeats, even while new leads are being written (they append at the end). There is deliberately NO server-imposed ceiling: the staff console legitimately reads a whole 57k-row brand, so a cap the caller cannot control would be a different bug, and an absent `limit` keeps the slim path on its single server-side `.cursor()` query, byte for byte as before. A bound arrives at the DATABASE (`LIMIT`/`OFFSET` on the outer query, chunk size clamped to what is still owed): a `limit=50` read hydrates, delivery-overlays, audience-resolves and serializes 50 rows, not the brand's population — that is why the common case is cheap rather than merely capped. Every unparseable bound (`limit=0`, `limit=abc`, `offset=-1`, a cursor this endpoint did not issue, `cursor` AND `offset` together) is a 400 before any work starts. Do NOT make any of them a silent fallback: this endpoint accepted `limit` and dropped it for months, answering 112 MB with a 200 to callers asking for 50 rows, and a silently-ignored bound is invisible by construction — nothing anywhere goes red. Route tests must assert the bound reaches the SQL, not just that the array is short (`tests/unit/lead-list-walk.test.ts` mocks `sql` so it honours LIMIT/OFFSET/keyset; a mock that returns a fixed slice would pass a handler that drops the bound). **The cursor's `createdAt` is `Date | string` and normalizes at ENCODE time — the `toIsoTimestamp` hazard above applies to it, because a cursor is built straight off a raw `sql` row: typing it `Date` and calling `.toISOString()` shipped green, then threw `is not a function` on the first production request, mid-stream, which destroys the socket instead of producing a clean 500. Test fixtures for these paths must use a raw timestamp STRING (`"2026-01-01 00:00:00+00"`), not `new Date(...)`; a Date fixture passes a handler that is broken in production. **Its write-side twin bit on the very next request: a DECODED cursor holds a real `Date`, and binding that into the keyset predicate throws postgres.js's `ERR_INVALID_ARG_TYPE ... Received an instance of Date` at Bind time — so the timestamp is bound through `leadCursorTimestampParam` (ISO string), never raw. The `sql` mocks in `tests/unit/lead-list-walk.test.ts` / `leads-route-page.test.ts` carry an `assertBindable` that throws on a `Date` param exactly like Bind does; without it both halves of this ship green.** **The position itself is `created_at::text`, selected as a SECOND column alongside the typed one and carried through the cursor verbatim: `timestamptz` holds MICROseconds and a JS `Date` holds milliseconds, so rendering a position through a Date floors it and the next page re-reads everything inside the dropped microseconds — a full production walk of a 57k-row brand returned 57,737 rows for 57,622 people (115 repeats, no gaps) before the text column existed. Never build a cursor from the typed `createdAt`.** (#417, v0.52.1, v0.52.2, v0.53.1.)
- **A figure computed over a brand's WHOLE population reads `?view=compact`, and a bounded page is ONE statement that cuts its rows BEFORE joining anything onto them.** features-service walks every lead of a brand to compute its revenue, funnel counts and per-lead outcomes. Measured in production on the largest brand (49,792 rows) that walk was **110 MB over 10 pages in 82 s**, and two causes stacked. (1) **The page was cut AFTER the per-lead joins.** `basicLeadQuery` put the keyset position and `LIMIT` on the OUTER query, so Postgres joined the person, the current employer and the primary email onto the brand's WHOLE deduped population and only then sorted and kept 500 — ~1.2 s per chunk, ~1.05 s of it lookups for rows the `LIMIT` threw away — and `streamBasicLeadChunks` issued a SEPARATE statement per 500-row chunk of a bounded page, paying that ten times per 5,000-row page. The scope filter, keyset and `LIMIT`/`OFFSET` now live in an INNER subquery and the lookups run on the page alone, and a bounded page is one statement streamed through `.cursor()`. A/B'd in the production container against the previous build: the same 10-page walk went 70.2 s → 5.4 s with **zero** differing rows out of 49,792. Do NOT move the page cut back to the outer query, and do NOT go back to a statement per chunk. (2) **`view=basic` carried ~2.2 KB a row of which the engine read a quarter**, and resolved an audience, an offer and a standing per chunk that it never read. `view=compact` (`toCompactLead`, `src/routes/leads.ts`) is the row a figure needs — id, leadId, campaignId, workflowSlug, status, email, the delivery flags and the identity/firmographics a per-lead row renders — every value read off the SAME row and the SAME flattened overlay `view=basic` emits, so switching views cannot move a figure (`tests/unit/leads-compact-view.test.ts` asserts field-by-field equality against basic). It runs none of the audience/offer/standing resolvers, refuses `include=campaigns` with a 400, and is gzip-encoded when the caller accepts it. **The gzip is scoped to `view=compact` on purpose**: every other response keeps its exact encoding, because a proxy that decodes a body and copies `content-encoding` onto it would hand an existing consumer garbage. Envelope, paging and filters are identical to `basic`. Do NOT add fields to `compact` for a consumer that is not computing over the whole population — that is what `basic` is for.
- **A compact row carries the positive reply the customer's CRM evidences — `crmPositiveReplyAt`, `src/lib/crm-positive-reply-dates.ts`.** The CRM evidence pass writes a CRM form submitted after our first delivered email as `conversion_events.event='positive_reply'`, `source='crm'`, `lead_campaign_id` NULL (per brand × lead). It is deliberately NOT a step outcome, so `/conversion-counts` and `/converted-leads` do not carry it, and features-service counts positive replies from the compact rows — so without this field its stat cards, cost per positive reply and ROI never saw the reply the Leads bucket shows. The field is SEPARATE from `replied`/`replyClassification` so the delivery facts stay exactly what the sender measured; a consumer counts a person once when either says positive. Earliest date across the row's brands; live + attributed rows only. The change feed carries it too; a new CRM reply reaches a feed on its next reconcile (bound 3 — no trigger fires on a `conversion_events` write). (Set 2026-09-25.)
- **A read never holds the population — not to count it, not to order it, not to export it.** The index pass that lets a tab state its size and an export stream the whole list used to build the WHOLE matching set in memory before answering: one row per person carrying its delivery overlay, its bucket set and its outcome set, about 3.4 KB each. On the largest brand's export (16,599 rows) that is ~160 MB of peak heap against a 384 MB V8 cap, so `FATAL ERROR: Reached heap limit Allocation failed` killed the process on every press — **exit code 0**, `OOMKilled: false`, restart policy up in seconds, `/health` green, `RestartCount: 10` in six hours and nothing anywhere red. The only trace was `ECONNREFUSED` in callers' logs, which is every OTHER org's Leads page going down because one customer pressed Export. Four things are load-bearing. (1) **The population is WALKED, never fetched** — `streamLeadIndex` streams one statement through a server-side cursor a chunk at a time (it used to issue a statement per chunk, each re-running the brand's whole dedup: 4.8s of a 17,910-person walk); there is deliberately no array form, because one would be used. (2) **The ORDER and the COUNTS live in the database**, in the scope's read model (`src/lib/lead-read-model.ts`, see the next bullet): a sort is the one part of a filtered read that is unavoidably O(the population), so it is an `ORDER BY ... LIMIT` over the model's rows and a count is a `GROUP BY` over them — this process holds one chunk at a time while BUILDING a model and nothing at all while READING one. The model's SQL and its freshness machinery are covered against a REAL Postgres (`tests/integration/lead-read-model-sql.test.ts`); a mocked `sql` compiles none of it, so route tests get `tests/helpers/fake-lead-read-model.ts` (rows derived by the real code, filter/order in JS) and prove wiring, not SQL. (3) *(folded into (2): a count is SQL over the model, O(1) in this process.)* (4) **Bytes leave as fast as the socket takes them** (`src/lib/stream-writer.ts`): `res.write()` never blocks, so ignoring its `false` return buffers the difference between database speed and network speed as heap — the same failure one layer down, growing with the same thing. Every streamed byte goes through `ResponseWriter`, which batches and waits for `drain`, and resolves on `close`/`error` too so a dead socket cannot hang a request holding a connection. So both stores carry `withdrawn_at`/`withdrawn_by_user_id` (migration 0035) and EVERY read that already filters `retracted_at IS NULL` filters it too — counts, by-day, `/converted-leads`, `/converted-lead-emails`, `/step-costs`, `/step-disqualifications`, the panel read, the measured-visit suppression set and the write path's own contradiction guard. Nothing is deleted: what somebody stated, and the fact they later withdrew it, both stay readable, the same posture supersession already takes. Four things are load-bearing. (1) **`withdrawn_at` and `retracted_at` are DIFFERENT facts and stay apart** — retraction is the funnel resolving a contradiction (an outcome proved the "never" wrong), withdrawal is the author saying it should never have been stated — so withdrawing an OUTCOME un-retracts the "never"s that outcome retracted (`retracted_by_step = <step> AND withdrawn_at IS NULL`, so one withdrawn on its own account is left alone), and restating any withdrawn statement clears the mark through the existing upsert. (2) **Implication re-derives on READ, as it always did**, so a step that only read as reached or as dead because of the withdrawn statement falls back to whatever the remaining statements imply with no extra write — and the response carries those re-derived `steps`, computed by the SAME `loadStepStates` the panel read uses, so a caller never guesses what its withdrawal did and the two surfaces cannot diverge. (3) **Only a statement a PERSON made is withdrawable**: a tracker-reported or delivery-measured outcome is 409 `not_a_statement` (this service does not edit what another system observed) and a step nobody stated is 409 `nothing_stated`, carrying `state`/`origin`/`impliedBy` so an implied step names the statement to withdraw instead — both distinguishable from a 500 by their `code`. (4) **Idempotent**: withdrawing what is already withdrawn is a 200 `alreadyWithdrawn: true` that writes nothing. Purely additive — the write is unchanged and no live caller can observe a difference.
- **A stated `sale` MUST carry `valueCents` (400 otherwise); every other step keeps it optional.** A won deal is the one place in the system where estimating has no excuse: with no value, every downstream money figure — pipeline, ROI, cost per acquisition — falls back to the brand's average lifetime revenue, a number that describes no real customer, and does it silently. The other steps stay optional deliberately, because an unusually large lead is worth stating early, long before it closes. This is a breaking request-contract change for whoever writes statements, so the dashboard must ask for the amount on a sale BEFORE this reaches production — consumer-first, per the deploy-ordering rule. (#450.)
- **Every step statement MUST state what that transition COST THE CUSTOMER (400 `cost_required` otherwise), and that money NEVER enters the platform's cost ledger.** The product sells a sales funnel one step at a time, and the steps the platform does not automate are performed by the customer — they run the meeting, they close the deal — so they are the only one who knows what that leg cost. Without it a funnel's cost of acquisition counts only the leg we billed for and every return displayed for that funnel is too good. `costCents` is required on BOTH kinds: a `never` carries one too, because a meeting that was run and went nowhere cost exactly what it cost. **Absent is a REFUSAL, never a zero, and the column is nullable rather than `NOT NULL DEFAULT 0` for the same reason**: `0` is a stated zero (a legitimate answer — the author chooses what goes in, zero, their time valued however they like, real expenses) and `NULL` is "nobody was ever asked" (every statement made before this shipped, and every tracker-reported outcome — a page-load tag observes a page load and knows nothing about a customer's spend). Defaulting the legacy rows to 0 would fabricate an answer nobody gave and the two could never be told apart again; that is also why the internal read answers `statedCount`/`unstatedCount` beside each total instead of a bare sum. **This money is the CUSTOMER'S**: it is recorded because they told us, never charged to them — no runs-service cost is provisioned/actualized for it, no billing authorize is called, nothing about it appears in the org's spend. The consumer read is `GET /internal/brands/:id/step-costs[?step=]` (one row per live hand statement, outcomes and `never`s alike, with campaign grain), plus `costCents` on each `/internal/brands/:id/converted-leads` row. Its set is deliberately NOT the set `/conversion-counts` counts, and that is not a contradiction because this is MONEY and that is a POPULATION: a hand-stated `website_visit` whose click the delivery layer already measured is suppressed from the counts (one visit, counted once) but kept here (the money was spent either way), while a RETRACTED `never` is excluded exactly as everywhere else, because the outcome that superseded it carries its own cost. Breaking request-contract change for whoever writes statements — the dashboard must ask for the amount before this reaches production, per the consumer-first deploy-ordering rule. (Migration 0034.)
- **Where a lead STANDS is decided here and nowhere else, per campaign, derived on read — `standing` on every `GET /orgs/leads` row and on `GET /orgs/leads/{id}`.** "Is this person still a live prospect" is COMMERCIAL POLICY, and it was decided in three independent places from two different sources with no owner: the dashboard computed it per lead off the reply signals, features-service counted an aggregate for the campaign's stat card, and instantly-service froze a coarse classification at write time that fed both. That split has already produced a customer-visible contradiction (instantly-service#649: a referral read as interest on one surface and not on the other, for months). This service is the only one holding BOTH halves — the delivery evidence it already joins onto the membership row, and the hand-stated step statements it owns — so the policy lives in `src/lib/lead-standing.ts` (pure) and everything else renders it. Five things are load-bearing. (1) **FUNNEL-AWARE, not funnel-agnostic.** `sales_interest` means "reached the step this campaign's funnel is ENTERED by", and that step is per funnel: a visit-led funnel is entered by a CLICK the delivery layer measures, a conversation-led one by a POSITIVE REPLY it classifies, and an ads-led one by an ad click nothing here observes. `FUNNEL_ENTRY` (`src/lib/funnel-steps.ts`) is that catalogue, and it is a different question from `FUNNEL_STEPS[key][0]` — a funnel's first STATABLE step is not always its first step, which is why `sales_meetings_from_conversation` starts its steps at `meeting_booked`. So the same click is `sales_interest` on `form_magnet` and `engaged` on a campaign that prices no visit; the `(lead, campaign)` grain is what lets both be true of one person, and the funnel comes from the CAMPAIGN (campaign-service `funnelKey`) exactly as the step statements' funnel does — never from the brand, never from a goal. The measured 67-click case that forced it: campaign `9e28ba26` sells `visit -> form -> paid`, 67 people clicked through, 0 replies were positive, and the customer's board showed zero cards under Sales interest. (2) **Precedence is evidence strength, and the opt-out is absolute — and it is its OWN state, `opted_out`, never a shade of `disqualified`.** An opt-out is the prospect's own act and legally binding; a disqualification is a commercial judgement of ours that we may revisit. They are two columns on the board, with different copy and different moves, so they must be countable and pageable APART — and a count cannot read `signal` off rows it deliberately never fetched. Splitting the STATE (rather than adding a second dimension) keeps the partition intact: a lead still has exactly one standing, so `standing-counts` still sums to `total` exactly, and `?standing=opted_out` / `?standing=disqualified` each page on their own. Precedence: unsubscribed (scope or global) > a human statement (an outcome on the funnel, then a `never`, both read through the SAME `resolveStepStates` the panel reads so the two surfaces cannot disagree) > bounced > the funnel's own entry step reached > a reply DISQUALIFICATION > engagement > contacted. A click plus a negative reply on a visit-led funnel is `sales_interest`: reaching the step is a fact about the funnel, a classification is a judgement about a message. Nothing overrides an unsubscribe — not a click, not a stated sale. **A negative reply is NOT a disqualification.** Disqualified means one thing: we realised this person is not our target — the wrong contact, or gone from the role — which is ordinary sales qualification (we sell pears to supermarkets and wrote to somebody in construction). A decline about the offer today is a judgement about the MOMENT: the person is still reachable and the lead is still recyclable, so they read `engaged` with `signal: "negative_reply"`. "They cannot buy" is the same thing. An opt-out is the prospect's OWN act, has its own column, and never shares one with a commercial judgement of ours — which is why it has its own STATE (`opted_out`); it used to be told apart only by `signal`, which a count could not do without fetching rows. The finer reading is DERIVED BY THE PROVIDER and forwarded through email-gateway's status read as `disqualified` (boolean, OPTIONAL); read that derived answer and never re-derive it from a list of reply kinds this service would then have to keep in lockstep with instantly-service. Absent is a THIRD state — a provider that does not track replies serves no reading, and neither does an older payload — and it is neither a yes nor a no: a negative reply with no disqualification reading answers `unresolved` / `reply_disqualification_unknown`, never a default in either direction. The merge across providers ORs only over the providers that ANSWERED (`mergeDisqualified`), so "nobody can tell us" survives a provider that never serves the field. (3) **NOTHING is fabricated and NOTHING is defaulted.** A row that was never served is `not_contacted` and is judged no further; an unscoped read (delivery layer never asked), an unresolvable funnel, and an unreadable statement each answer `state: "unresolved"` with the `reason` on the wire. `reachedEntryStep` is `null` — never `false` — on an ads-led funnel, because "no" would be a claim this service cannot make. A resolver failure downgrades ONE field, never the read: a 57k-row walk is not failed over a derived value. (4) **Derived on READ, never stored.** Retracting or withdrawing a statement moves the standing with it, with no write and no backfill, exactly as the panel's step states already work. (5) **Resolved ONCE per response.** `createLeadStandingResolver` reads the org's campaign -> funnel map in a single campaign-service call reused by every chunk, and folds in the measured visit from the delivery overlay the row ALREADY carries (a click IS the automatic half of `website_visit`) rather than making a second email-gateway call. The statements are two indexed reads per chunk, batched. Purely additive: every raw delivery fact stays on the row unchanged — they are what let the policy change later — and a consumer that ignores `standing` keeps working. Do NOT re-derive this in a consumer, and do NOT let a consumer add a signal of its own to it; that is the three-implementations split this closes. (#472.)

Now `caused_by_outreach` is the EFFECTIVE answer on every row — a person's answer, else the rule — so `byCause`, `/converted-leads` and a lead's closed deal fill in with no shape change. Four things are load-bearing. (1) **One rule, one place**: `outcomeCauseRule` IS `crmCauseRule` plus one precondition (no attributed lead -> `not_matched`); do NOT write a second date comparison anywhere, and do NOT let a consumer re-derive it from delivery timestamps. (2) **A person always outranks the rule**: their answer lives in `stated_caused_by_outreach` (backfilled from every existing manual cause — nothing else ever wrote one), the worker's every UPDATE is guarded on it being NULL, and restating an outcome without a cause returns it to the rule (the rule's stored answer is kept when the date did not move, dropped when it did). A CRM row's override stays in `lead_step_cause_statements`, untouched. (3) **The reason is stored**: `cause_rule` holds `{causedByOutreach, reason, firstDeliveredAt, leadId, occurredAt}` like `crm_evidence.rule`, and `/converted-leads` serves it as additive `causeBasis` (`person`/`rule`/null) + `causeReason`. (4) **A worker, not a read-time derivation**: the rule needs email-gateway's first delivery per person, which every count read would otherwise have to fan out for. `OUTCOME_CAUSE_INTERVAL_MS` (5 min) IS the bound on how long a new unanswered outcome reads null; a `never_delivered`/`not_matched` answer is re-evaluated every sweep (we may email them later, a match may resolve), a dated answer against a delivery is final. email-gateway failing leaves the brand's rows exactly as they were — never a guessed answer. Nothing about what COUNTS changes: a "not ours" outcome is still a real outcome of the brand.
- **One SALES FUNNEL of an offer is a scope — `?offerId=&funnelKey=` on `GET /orgs/leads`, `/bucket-counts` and `/standing-counts` (and so the CSV export).** An offer is routinely sold through several funnels at once, and the dashboard's per-funnel Leads page could only ask for the whole offer, so a lead reached through a sibling funnel showed under this funnel's tabs. The funnel narrows the SAME campaign-id set the offer scope resolves (`resolveOfferCampaignIds(offerId, ctx, funnelKey)`, `src/lib/offer-campaigns-client.ts`) to the campaigns that STATE that funnel on campaign-service's own `funnelKey` — so dedup, delivery overlay, read model (keyed on the campaign ids), order and search are the offer scope's by construction, and one funnel's population is always a subset of the offer's. Either spelling of a key is accepted (`canonicalizeFunnelKey`); unknown key, repeated key, or `funnelKey` without `offerId` are 400s — a silently ignored narrowing would state the offer's leads under the funnel's name. **A campaign stating no funnel belongs to NO funnel page, and that is never inferred** (not from the offer's declared funnels in brand-service, not from a sibling, not from a goal). Measured 2026-09-24: 325 offer-carrying campaigns state no funnel, and all but five are non-sales channels (PR, hiring, press kit, expert quotes, AI visibility) that must not appear on a sales funnel page anyway; the five are legacy `cold_email` rows (8 people on the two offers declaring a single funnel) and stay unattributed rather than guessed — if that ever matters, the fix is campaign-service stating their `funnel_key`, not an inference here.
- **Who a brand has WON is answered HERE, by email — `GET /orgs/brands/{brandId}/won-leads[?email=]` (`src/routes/won-leads.ts`).** human-service's per-brand suppression is a 3-month window on when someone was last SERVED and knows nothing about outcomes, so a paying client became servable again and got a cold email from the brand that sold to them. "Won" is exactly what makes a lead's standing `customer`: a live (`withdrawn_at IS NULL`), `attributed` `sale` (legacy `purchase` included) on `conversion_events`, whether a person stated it, the tracker reported it or the customer's CRM evidences it — every funnel ends at `sale`, so nothing is re-derived. Scope is (org from `x-org-id`, brand): all campaigns and offers of the brand, never another org claiming the same brand. Identity is EVERY registered email of the won lead, lowercased; `?email=` narrows the SAME statement, so the one-address check cannot disagree with the set. A withdrawn sale statement (or a CRM sale a person's statement superseded) drops out on the next read. Any failure is a 500, never an empty set — empty means "re-contact freely". Proven against a real Postgres in `tests/integration/won-leads-sql.test.ts`.
- **WHAT HAPPENED TO THIS PERSON is answered HERE, in one ordered read — `GET /orgs/leads/{id}/history`.** A customer opening a lead asks one question and nothing answered it: the dashboard assembled it IN THE BROWSER out of six services that do not speak to each other — the delivery evidence and the hand-made funnel statements here, the copy we generated and the planned cadence in content-generation-service, the real messages and the hand-recorded reply statements in instantly-service, the attributed outcomes in the conversion ledger, and the customer's own mailbox in google-service, which nothing read at all. It fetched all of it, de-duplicated it, sorted it and decided what to hide, so there was no source of truth for what happened to a person and every consumer invented one: a reply whose words we hold showed as a bare "they replied", follow-ups read as scheduled after the sequence had stopped, an exchange living only in the owner's mailbox was invisible, and a reply somebody recorded by hand read exactly like one we can produce. This service is the only one holding a lead as a PERSON rather than as an artifact of one campaign, so the assembly lives here (`src/lib/lead-history.ts`, pure; `src/routes/lead-history.ts`, the IO) and a consumer renders it without merging anything. Six things are load-bearing. (1) **NOTHING IS RE-DERIVED.** Every fact is asked of the service that OWNS it — clients in `src/lib/{outreach,mailbox,generated-email}-client.ts` — and no funnel or outcome logic lives in this read: a step statement is carried as the statement it is, never re-implied, so this is an ORDERING and not a second brain. (2) **ASSERTED IS NOT OBSERVED AND THE ANSWER SAYS WHICH.** `evidence: "observed"` is a fact we hold (a message whose words we can produce, a milestone the delivery layer measured, an outcome the tracker reported); `evidence: "asserted"` is a fact somebody stated. Within replies the distinction is carried by TYPE rather than a flag a consumer must remember: a reply we hold the words of is a `message`, a reply somebody wrote down because it never reached us is a `reply_statement` and carries no body, because there are no words to carry. `bodyStatus` keeps the third state — we hold the message and could not READ it — apart from a message that genuinely says nothing. (3) **SCOPE IS STATED.** `scope=campaign` (default) resolves the campaign's whole IDENTITY exactly as every other campaign-scoped read here does; `scope=brand` rolls up every campaign of the brand this person is in. Both are legitimate questions and the response says which it answered and names the campaigns it asked about. (4) **A SOURCE THAT COULD NOT BE READ IS STATED AS UNREACHABLE.** Every source carries its own `status` + `reason`, one failing degrades ITSELF and sets `complete: false`, and none of them can take the read down — "we could not read this" and "this did not happen" are different facts, and collapsing them tells a customer their prospect said nothing. A bounded fan-out says so too (`campaignsTruncated`), because a capped answer must never look like a whole one. The only 500 is this service's own data being unreadable. (5) **THE DE-DUPLICATION THE BROWSER WAS DOING HAPPENS HERE.** A `sent`/`replied` delivery milestone is suppressed when the message carrying those words is already in the list, **the copy we DRAFTED (`generated_email`) is suppressed for a campaign whose outbound message we hold — the draft and the send are the same email, hours apart, worded differently (no signature, no unsubscribe line) and with the link written differently in each, so stating both showed one email twice; it is still stated for a person nothing has been sent to yet, where it is the only thing we have**, and one message mirrored on both the outreach side and the customer's mailbox is ONE event naming both (`heldBy`) — matched on direction, minute, normalized subject and the head of the body, because two mirrors of one message agree on the minute and not on the second. **A `message` carries its LINKS — what the prospect SAW and where each truly leads (`links: [{text, href}]`, `src/lib/message-links.ts`).** The sending side strips our tracking parameters from a link's visible text on purpose (the prospect reads a clean URL) and replaces the destination with the provider's own click-tracking redirect, so the body we hold carries NEITHER our parameters nor the real destination and a reader cannot see or follow where the link went. Nothing new is fetched to answer it: the generated copy this read already fetches carries the same URL WITH its parameters, so destinations are indexed off it (`bodyText`, `bodyHtml`, and the planned sequence scanned as text, since its shape is the producer's). The match keys on origin + path — exactly what survives the strip — with host case, a leading `www.` and a trailing slash treated as spelling; the query string is what was removed, so the match must not depend on it. Three things are load-bearing. (1) **`href` is only ever a URL WE WROTE**, which makes the provider's click-tracking redirect unreachable as a destination by construction (it appears in no generated copy) — following one from a dashboard would register a click the prospect never made. (2) **Unresolvable is stated, never guessed**: a link matching no URL we wrote, or matching SEVERAL different parameterizations of one page, carries `href: null` beside the text the reader saw. Choosing between two parameterizations would be inventing tracking parameters. (3) It is **purely additive** — the drafted copy for an unsent lead reads exactly as it did, and a consumer that ignores `links` is unaffected. **A `clicked` delivery milestone says WHERE the click went (`destination: {state, href, resolution}`), or says it cannot.** A click is the moment a cold prospect became interested, and stating it without naming the page reads as a bare claim; the reader cannot work it out for itself, because joining a click to the messages around it is exactly the merge this read exists to own. The delivery layer measures THAT a click happened and never where it went — the outreach provider's click webhook carries 20 fields and no URL, which is ~2,339 of 2,610 non-inferred clicks — so the destination is resolved against the copy we wrote to that person ON THAT CAMPAIGN, off the index the links above already build (nothing new is fetched, and the provider's click-tracking redirect is unreachable as a destination for the same reason). Measured on production content-generation, 9,033 of 9,063 generated emails carry exactly ONE distinct destination, so `state: "known"` is the ordinary case. Three things are load-bearing. (1) **AMBIGUOUS AND UNKNOWN ARE DIFFERENT FACTS.** Several candidate pages — or several parameterizations of one page, where picking would be inventing tracking parameters — is `ambiguous`, i.e. there is nowhere honest to point; nothing resolvable at all is `unknown`, i.e. we have no opinion. Collapsing them would tell a consumer the same thing about two different situations. (2) **`resolution` SAYS WHETHER THE ANSWER WAS MEASURED OR REASONED TO.** `observed` is a record of the destination itself — instantly-service holds one per hit in `tracking_hits_raw.payload.url` for mail dispatched through our own click redirect, with `sourceRowId` pointing back at it from the promoted event (~186 of 2,610) — and it does not SERVE that record today, so every destination this produces is `deduced` and says so. Wiring `observed` is a producer change, not a licence to relabel a deduction. (3) It is **purely additive and scoped to the click**: `destination` is present on the `clicked` milestone and on no other, so a history with no click is byte-identical to what it always was. (6) **NOTHING DEPENDS ON THE OUTREACH PROVIDER STILL BEING SUBSCRIBED.** instantly-service reads its own bronze mirror of the Unibox and this service never talks to the provider; the Gmail mirror is for some prospects the ONLY copy of a conversation. Cost is one page view: one email-gateway call for the PERSON (brand scope, then each campaign's own evidence read out of the breakdown with `flattenCampaignSubsetStatus` — never the brand roll-up stamped on every campaign), one Gmail-mirror call, one recorded-reply call, one recorded-opt-out call and two per campaign in scope, bounded to `MAX_HISTORY_CAMPAIGNS` with six requests in flight. Withdrawn and retracted statements are filtered exactly as every other read here filters them. Requires `INSTANTLY_SERVICE_*`, `GOOGLE_SERVICE_*` and `CONTENT_GENERATION_SERVICE_*` in the env.

## The company facts and the career history are CARRIED and PERSISTED, never derived here

A cold email is written by an LLM from the person and company facts the served lead payload carries, so a null company description is a worse email. apollo-service has always held that material — measured in prod on 2026-09-09 over the last 30 days it holds a company short description for 94% of enriched people, keywords and technology names for ~100%, a founded year for 79%, a latest funding stage for 21% and a FULL employment list for 100% — and none of it reached a lead: human-service's neutral organization was a small subset and carried no career history at all, so lead rows for the same people held 3.1% / 3.2% / 2.8% / 0.6% and exactly one employment row each (avg 1.00). Downstream, the company-description, keywords and tech-stack prompt variables rendered EMPTY in 87% of the 11,070 sales emails generated in that window, and funding stage in 100%. `leads.metadata` looked like it held the answer and did not — Apollo's people-SEARCH response carries the organization object with those keys NULL; only the ENRICHMENT does, and only apollo-service stores it.

Four things are load-bearing. (1) **Persisted at WRITE, never derived on read and never fetched from a sibling at read time.** `pickOrgFields` (`src/lib/leads-registry.ts`) copies the widened neutral organization onto the `organizations` row and `recordEmploymentHistory` writes one `leads_organizations` row per role. Nothing is inferred: not from the domain, not from the name, not from the industry. human-service owns the values, this repo carries them, and a field the producer did not send leaves the column ALONE — an absent key and a null are both "nobody stated this", so a re-serve can never blank a column an earlier richer serve (or the backfill) filled. An EMPTY array is not a stated value either. (2) **Every widened field is OPTIONAL on the wire.** The eleven fields the gateway has always served keep their exact types; everything else is `?` on `PersonOrganization`, so the service behaves byte-identically against a producer that serves none of it, and started filling the moment human-service's own widening went live. Nothing in `FullLeadSchema` changed — the columns and the served shape ALREADY declared all of this; only the write path was narrow. (3) **The top-level organization is the CURRENT employer and the only rich one.** A past employer is known by NAME alone (the provider carries no domain for one), so those rows key on the name and land on an existing organization when the company is already known. Employment rows are matched on (organization, start date) and a pre-existing row carrying NO start date is ADOPTED, not duplicated — that is what makes the single-row shape written before this converge instead of doubling. Exactly one row is current, and that is enforced against the provider rather than assumed from it: a person routinely holds several CONCURRENT titles at ONE employer ("Founder & Chiropractor", "Educator & National Speaker", "Founder & Director", all flagged current, none with a start date) and those are ONE employment wearing three titles, so roles are resolved and keyed on (organization, start date) BEFORE anything is written and duplicates merge — keying them row by row produced three `current = true` rows for one lead and made `currentTitle` a coin flip. When two different employers are both flagged current, the top-level organization wins (it is the producer's own answer to where this person works) and the other role is still recorded, just not as THE current employer. Absent any current flag, the top-level organization is current. Nothing is ever deleted. (4) **A role's date is a calendar date or it is nothing** (`normalizeEmploymentDate`): an unreadable date leaves the ROLE recorded with a null date and says so in the log — losing a career fact over a provider formatting quirk would be worse, and inventing the date would state something nobody told us.

Historical rows are repaired by `scripts/backfill-lead-org-enrichment.ts` off `scripts/sql/apollo-lead-org-enrichment.sql`, which is a plain SELECT against apollo-service's own `apollo_people_enrichments` — no Apollo API call, no key decryption, no credit authorization, so it CANNOT spend a credit (driving it through apollo-service `POST /enrich` would have bought on every cache miss, and that route's cache hit additionally requires a verified email newer than 12 months). It is dry-runnable, idempotent (a column is filled only while it is NULL, so a re-run converges to 0 and a live write is never overwritten) and exactly reversible from its `--report` file, which records the organization id plus the columns filled and the id of every employment row inserted. Do NOT generalise it into a recurring sweep: the live path persists at serve, and the affected set is closed.

## `businessLanguages` is CARRIED, never derived here

human-service derives, per person, the language(s) they plausibly conduct business in and exposes them as `businessLanguages` (ISO 639-1 lowercase, ORDERED most-plausible-first, empty array = no usable signal). lead-service sits between that producer and content-generation-service, which writes each cold email in the recipient's language rather than always in English. This repo's only job in that sequence is to carry the value through intact.

- **Never derive, infer or guess a language here** — not from `city`/`state`/`country`, not from the name, not from the organization. human-service owns the derivation and the vocabulary; a second implementation would drift from it silently. `tests/unit/lead-business-languages.test.ts` guards this.
- **Order is the contract.** The end consumer selects by position (index 0 = most plausible), so the column is a Postgres `text[]` precisely because it preserves insertion order. Never sort it, de-duplicate it into a set, or normalize it.
- **Three states, all distinct, none of them a guess**: `NULL` = the lead predates the field being carried; `{}` = the producer had no usable signal; `{en}` = known to be English. Do not collapse `{}` into `NULL`, and never substitute a default for either.
- **Nothing is backfilled.** The column is only ever written from real producer data, via `PERSON_FIELDS` in `src/lib/leads-registry.ts` — presence in that list IS the write path (`pickPersonFields` copies the key straight off the neutral `Person`). Added 2026-08-26 alongside human-service v0.40.0.
- The neutral `Person` (`src/lib/people-client.ts`) is a pass-through cast of human-service's response, so the field arrives populated with no mapping code; `src/lib/lead-shape.ts` emits it on both the single and batch `FullLead` paths.

## Boot — the port opens BEFORE migrations, and traffic is gated until they finish

- **`app.listen()` runs FIRST; `migrate()` runs behind it.** This was learned on Neon, whose computes suspended after inactivity: a deploy landing on a cold compute spent its whole startup budget on the first connection, so the port never opened inside Railway's 30s healthcheck window (`1/1 replicas never became healthy!`, with no application output at all — not even "Migrations complete" — because the stall happens before any logging), or the connection was refused mid-resume and the old `.catch(process.exit(1))` turned it into a restart loop. Neon and Railway are both gone; the failure SHAPE is not. Any moment the database is not ready to accept a connection right now — the Postgres container restarting, the box rebooting, a deploy restarting things underneath — reproduces it exactly, and `deploy.sh`'s health check will roll the release back for a port that never opened. The failure has nothing to do with the code being deployed, which is what makes it expensive: it reads as a flaky deploy, you retry, the DB is up by then, it passes. Do NOT move migrations back in front of `listen()`, and do NOT add pre-listen startup work (`registerProviders()` used to be there too — it now runs after readiness, non-fatal, because publishing metadata to key-service is not schema and a key-service outage must not hold the service at 503).
- **Opening the port early is only safe because `requireBootReady` (`src/middleware/readiness.ts`) 503s every route until migrations complete.** The service must never serve a request against a schema its code does not expect. `/health` is mounted BEFORE the gate; everything else after it. Keep that order when adding routers.
- **`/health` is boot-state-aware and must NOT ping the DB while `starting`.** Three states (`src/lib/boot-state.ts`): `starting` → 200 `{status:"starting",migrations:"pending"}` with no DB access (a database not yet accepting connections would otherwise fail the ping and take the deploy down — the exact bug, originally a Neon compute mid-resume); `ready` → the usual `SELECT 1` ping; `failed` → 503 naming the migration error, so the deploy's health check fails loudly and `deploy.sh` rolls back to the previous build. On migration failure the process deliberately stays ALIVE rather than `process.exit(1)` — exiting produces a restart loop that shreds the logs carrying the reason.
- **Migration retry is connect-phase ONLY (`withConnectRetry`, `src/lib/db-retry.ts`).** A rejected connection never dispatched a statement, so retrying it cannot half-apply a migration; a real migration error (bad SQL, failed constraint) is NOT retried and surfaces on the first throw. Budget ~65s, front-loaded (250ms → 8s) — sized to cover a Neon resume many times over when it was written, and it comfortably covers a Postgres container coming back up. Transient detection walks `cause` chains and `AggregateError.errors` (Node-20 happy-eyeballs produces one sub-error per candidate address) and matches driver codes, SQLSTATE class 08, `57P03` (`cannot_connect_now` — Neon returned it while resuming, and Postgres returns it while still starting up), and the code-less pool-acquire message `timeout exceeded when trying to connect`.
- **Do NOT "fix" cold starts with postgres.js connection options.** `connect_timeout: 30` is already the postgres.js default (`postgres/src/index.js`), so setting it is a no-op; `idle_timeout` defaults to `null` (idle connections are never closed), so setting a value makes them close and buys a fresh TCP+TLS handshake on the next request — that advice is correct for node-postgres, whose default really is an aggressive 10s teardown, and was mis-transplanted. Both were tried and reverted in brand-service#389. The one connection-layer setting kept here is `net.setDefaultAutoSelectFamilyAttemptTimeout(5_000)` in `src/db/index.ts`, which widens Node 20's 250ms per-candidate happy-eyeballs budget so the first connection to a database that is not yet ready is not aborted before it is answered.
- **A test file that `vi.mock`s `src/db/index.js` MUST `vi.resetModules()` between cases.** Without it the mocked module registry leaks into LATER test files in the same worker, and the symptom lands nowhere near the cause: `tests/unit/stats-persona-attribution.test.ts` hung to a 5s timeout, deterministically, because `health.test.ts` ran before it without the reset. Import the boot-state singleton through the same fresh registry as the route under test (a static top-level import binds to a different instance after `resetModules` and silently stops driving it) — see `tests/unit/health.test.ts`.

## A database connection is never held by a caller who left

- **The pool ceiling, and how long one connection may be held, are stated in `src/db/index.ts` — never inherited.** postgres.js defaults to `max: 10`, and on 2026-09-07 that default WAS the outage: ten concurrent whole-population lead reads arrived at 18:59:06 UTC, each took a connection, and none gave it back. Postgres held ten backends at `state=active, wait_event_type=Client` for 11h30m; the pool was permanently exhausted, every later read hung forever, `/health` answered 503 for 11.5 hours and only a manual `docker compose restart lead-service` recovered it. `RestartCount` was 0, so nothing cleaned the sockets on its own. `POOL_MAX` (20), `STATEMENT_TIMEOUT_MS` and `IDLE_IN_TRANSACTION_TIMEOUT_MS` are read together, each overridable by env, and an unreadable override THROWS rather than falling back to a default nobody chose. The two timeouts ride in the startup packet, so they bind this service's own sessions and nothing else on the shared Postgres — do NOT reach for a server-wide `statement_timeout`, which would change behaviour for ~20 services at once.
- **A long read asks between chunks whether anyone is still listening — `watchClient` (`src/lib/client-abort.ts`).** The unbounded `/orgs/leads` walk uses one server-side `.cursor()` for the whole population and does per-chunk gateway work between Executes, so the connection is held for the WHOLE walk. An upstream caller that gives up at its own 300s HTTP timeout closes its socket and stops reading, and nothing here noticed. So both streaming loops call `client.stopIfGone(rowCount)` at the top of each chunk, before that chunk's delivery/audience/standing fan-out. It THROWS (`ClientGoneError`) rather than breaking quietly: leaving the generator is what closes the cursor and hands the connection back, and a truncated stream must never be mistaken for a complete one — the route logs a warning and destroys the socket the caller had already stopped reading. It is not an error of ours, so it is a `warn`, not an `error`. Do NOT turn this into a flag checked after the walk; the release is the point. The bound is on ABANDONMENT, not on size: a legitimate 66k-row read of the largest brand still walks to the end.
- **`/health` reads its OWN two-connection pool (`healthSql`).** Liveness needs a socket and a `SELECT 1`, and during the incident it queued behind the wedged reads and reported this service unavailable when it could still have answered. Keep it off the main pool.

## Outbound-call resilience & route error handling

- **ALL outbound calls to runs-service go through `fetchWithRetry` (`src/lib/fetch-retry.ts`), never raw `fetch`.** runs-service used to sit behind Neon scale-to-zero, so the first call after an idle suspend landed mid-wake (~1-7s resume) and aborted the old raw `fetch(..., { signal: AbortSignal.timeout(5_000) })` with a `TimeoutError`/socket-reset. Scale-to-zero is gone, the failure is not: a sibling that is restarting, redeploying, or coming back with the box still refuses or resets the first connection the same way. `runs-client.ts` + `trace-event.ts` now use `fetchWithRetry` (connect-phase retry on `ECONNRESET`/`ECONNREFUSED` — write-safe, request never reached the server) + a 30s timeout (fleet norm; 5s was the outlier that couldn't fit a slow first connect). Any NEW runs-client function (or any client to a sibling service on a fail-loud path) must use `fetchWithRetry`, not raw `fetch`. (#390, v0.44.1.)
- **The SERVE PATH's own sibling reads are the ones this rule is for, and the rule reads as being about runs-service, so it gets skipped: `pullNext` calls campaign-service (`campaign-client`, the campaign's offer) and brand-service (`brand-client.getCurrentGoal`, the goal), and both must stay on `fetchWithRetry`.** A serve is the one request here that cannot simply be retried by a human, and its two sibling reads feed each other: the offer read's answer is what makes the goal read answerable at all on a multi-offer brand. So a connect reset on the campaign read does not merely lose a field — it drops the offer, and brand-service then refuses the goal read with 409 `SEVERAL_OFFERS`, i.e. exactly the production failure v0.80.1 shipped to fix, reappearing with nothing but a `console.warn` to show for it. A sibling mid-restart is the ordinary case, not an outage. campaign-client keeps a deliberate **5s** budget (a DAG retry must not wait minutes on a hung campaign-service) rather than the 30s fleet norm, and the backoff shares that deadline, so an exhausted budget degrades to exactly the pre-retry behaviour. The retry is connect-phase ONLY: a completed answer — including that 409 — is a real answer brand-service produced and still fails loud, once. Do NOT reach for a raw `fetch` in a new serve-path client, and do NOT widen the retry to HTTP statuses. (#541, v0.80.2.)
- **A brand-service read scoped to the BRAND is refused on a brand selling several offers, so a dead client pointing at one is a latent copy of that bug, not harmless dead code.** `fetchExtractedFields` (`/internal/brands/:id/extracted-fields`) and `extractBrandFields` sat here with zero callers while the route they read carries the same `SEVERAL_OFFERS` refusal `runtime-context` does — the next caller would have rediscovered v0.80.1's outage from scratch. Both deleted in v0.80.2. When a brand-service read comes back, it names the campaign's offer the way `getCurrentGoal` does, or it does not ship.
- **An `async` Express route handler's throw does NOT become a 500 automatically (Express 4) — it rejects the handler's promise, which Express ignores → `unhandledRejection` + the caller's socket HANGS with no response.** So any `await` in a route handler that can throw MUST be inside a `try` that `return res.status(5xx)`s. The trap: work done BEFORE the main `try` block (idempotency lookup, in-flight guard, `createRun`) is unguarded — a runs-service outage there escaped as an unhandled rejection instead of a clean 500. `POST /orgs/buffer/next` wraps its entire pre-serve block. When adding pre-`try` setup awaits to a route, extend the guard. Route tests must assert 500-on-throw with NO error middleware mounted (Express 4 wouldn't forward the async rejection to it anyway) — see `tests/unit/buffer-route.test.ts`. (#390, v0.44.1.)

## API Design Rules

- **Minimal request body.** Everything that workflow-service auto-injects as headers (`x-org-id`, `x-user-id`, `x-run-id`, `x-campaign-id`, `x-brand-id`, `x-workflow-slug`, `x-feature-slug`) MUST be read from headers, never duplicated in the body.
- **No `.default()` on Zod fields.** If a field is needed, make it required. A missing field is a 400, not a silent default.
- **No optional "convenience" fields.** If the service can fetch data internally (campaign context from campaign-service, brand fields from brand-service), do NOT accept it as a body parameter. Fetch it yourself. **This extends to identity HEADERS, not just body fields: a header carrying a producer-owned attribute that is *derivable* from an entity already identified by another header must be fetched, not required.** The `goal` (signup|meetingBooked|purchase) is a brand attribute (brand-service `brands.currentGoal`), derivable from `x-brand-id` via `GET /internal/brands/:brandId/runtime-context` — so lead-service fetches it inside buffer/next, never requires `x-goal` (v0.25). Carve-out: headers that ARE the request's identity (`x-org-id`, `x-campaign-id`, `x-brand-id`, `x-run-id`, `x-audience-id`) stay headers — they name *which* entity, they are not derivable attributes OF it.
- **Audience selection is campaign-owned — lead-service NEVER re-ranks/re-selects.** campaign-service decides the priority audience per run (`internal.ts` → features persona-stats) and propagates it as `x-audience-id` to every downstream DAG node. `buffer/next` serves the audience named by `x-audience-id` (`req.audienceId`) directly; no `x-audience-id` ⟹ clean `found:false` (campaign selected none). Do NOT re-introduce a features-service `persona-stats`/`getTopAudienceId` call in lead-service — that duplicated, divergent selection let an uncommitted audience be picked and 422 at serve-next (v0.26.1 removed it). Serveability (audience has a committed provider) is enforced upstream in human-service; lead-service treats serve-next 422 "no committed provider" as `found:false` (reason `audience_not_serveable`), never a 500.
- **Every empty serve NAMES why it is empty, and exactly ONE name means a population ran out.** `POST /orgs/buffer/next` answering `{ found: false }` in silence made five unrelated situations byte-identical on the wire, and the caller acts on one of them irreversibly: campaign-service stops the campaign, and funding a channel deliberately never revives a campaign stopped for exhaustion. So `found:false` always carries a `reason` (`src/lib/serve-reasons.ts` owns the vocabulary — the Zod enum reads `SERVE_EMPTY_REASONS` from it, so the published contract cannot drift from what the serve path returns). Only `audience_exhausted` is evidence about a population: human-service walked the audience this service was told to serve and reported nobody left. `no_audience` (no `x-audience-id`, so this service — which never picks audiences — looked at nobody), `serve_timed_out` (the budget expired mid-look), `audience_not_serveable` and `credit_insufficient` all state that no exhaustion was observed. A consumer decides "may outreach stop?" by testing `reason === "audience_exhausted"`, never by excluding known-benign values, so a reason added later defaults to not-exhaustion. The `no_audience` branch is NOT a bug to fix by picking an audience here — see the campaign-owned-selection rule above; it is a bug to report as exhaustion. Cost: brand `75d7e3e8`'s second cold-email channel (campaign `4769db14`, 2026-08-20 10:08:10) asked for the first time, got no `x-audience-id`, returned in 26ms without one network call, and was stopped `audience_exhausted` at 10:08:11 — while its sibling campaign served 109 leads for the same brand, same four audiences, the same day. (#439.)
- **`pullNext` drains the already-paid pool BEFORE asking human-service for anyone new.** A serve is billed (apollo/apify enrichment) and suppressed for three months in human-service the instant it happens, so a failure at ANY step after the serve — email generation, the vendor push, anything — strands a prospect the brand paid for and can never be offered again: `serveNext` correctly answers "someone NEW", and the suppression it consults is a PRE-payment guard that must not be relaxed (it is what stops us re-buying a person we already own). The gap was on this side, and so is the fix (`src/lib/retry-pool.ts`): this campaign's own `status='served'`, `sent_at IS NULL` rows, oldest serve first, bounded to `RETRY_CANDIDATE_BATCH_SIZE`, resolved by ONE batched campaign-scoped email-gateway `/orgs/status` call. **The SENDER's own `queued` statement decides first** (broadcast scope, forwarded whole by email-gateway from instantly-service): `queued: true` ⟹ never re-served, whatever its age; `queued` absent (no broadcast half in the gateway's answer, or a payload without the field) ⟹ `unknown`, NOT retried and logged loudly — never read as false. The age guess only applies where the sender says it holds nothing (`queued: false`): `contacted` false ⟹ re-serve now; contacted-but-not-`sent` ⟹ wait, bounded by a **5-day** TTL measured from our own `served_at` — past it the vendor lost it, re-serve. Cost of the age-only guess (2026-09-21 → 09-24): instantly-service's queue backlogged past five days, every lead in it read as lost, and each re-serve hit the vendor's idempotent duplicate and sent nothing — campaign `f7b1b610` made 1,643 send attempts over 145 people in a day (one person re-served 38 times) and new-lead serves fell from ~400/day to ~50, because each re-serve takes the slot that would have bought someone new. Five and not three because a lead queued Friday evening leaves Monday morning and a bank holiday pushes that past three days, and the error is asymmetric: stranding a lead is recoverable, a second email to a human is not. **The sender's `finished` statement closes a person for good** (`finished: true` on the broadcast scope: it holds their `(campaign, email)` claim with nothing left to send, so every further hand-off to that campaign is a duplicate that sends nothing) ⟹ `sender_closed_at` is written (migration 0039) and the row never re-enters the pool. It is NOT `sent_at`, which the lead history reads as an email that went out; `queued` and `sent` both outrank it; absent is never read as false. Cost of not having it (#568): campaign 3922c8e1 handed the same people out 104 times each, zero emails. The other half of #568 — the sender refusing a person whose lead id lead-service had repointed (#393) — was fixed in the sender (instantly-service v0.82.34 re-keys onto our id). `sent` ⟹ `sent_at` is written and that person is never returned and never re-queried again — that marker is the only thing keeping the gateway call small as a campaign ages. The winner is taken by a conditional `UPDATE ... RETURNING` on `retry_claimed_at` (an hour-long lease, re-pointing the row's run ids at the claiming run), so two concurrent pulls cannot hand the same person to two runs and a claim that fails downstream is retryable the same day; the lease also doubles as the queue position, so a repeatedly-failing person sorts to the back instead of blocking the head. **The claim does NOT write `status='claimed'`** even though that value exists in `LEAD_LIFECYCLE_STATUSES` and nothing else writes it: the delivery overlay and the dedup winner ordering both key on `status='served'`, so demoting a row that WAS served would silently blank its engagement in `GET /orgs/leads`. email-gateway unreachable is FAIL-CLOSED — fall through to `serveNext`, which merely costs money, rather than guess and send a second email. Empty pool ⟹ one extra indexed SELECT and then byte-identical behaviour. Do NOT turn any of this into a cron or a sweep: it belongs on the serve path, which is the only place that knows a person is about to be handed to a workflow. (#443, second occurrence of the shape after #408.)
- **What we owe a prospect NEXT is stored per (lead, campaign), and exactly one worker may act on it — `followup_due_at` + a claim lease on `leads_campaigns` (migration 0036, `src/lib/followup-queue.ts`).** Once somebody shows a sales interest we owe them an answer now and, if they go quiet, further answers at growing intervals, indefinitely; nothing recorded that debt, so a worker wanting to answer the next person due had nothing to ask. Six things are load-bearing. (1) **The claim is the SAME conditional `UPDATE ... RETURNING` shape the paid-pool retry uses (0030), not a second concurrency mechanism** — several replies land in the same instant and a read-then-write race would send a second email to a human, which is the one failure here that cannot be taken back; the lease EXPIRES (an hour) so a worker dying mid-answer strands nobody. `POST /orgs/campaigns/{campaignId}/followups/claim-next` returns at most one person, exactly once. (2) **The interval is the WORKER's choice, stored, never computed here.** A prospect who writes "recontact me in January" must be honoured, so the next due date arrives as data on `POST /orgs/leads/{id}/followups`; this service only BOUNDS it (never in the past beyond a 5-minute clock-skew tolerance, never further out than a year) and REFUSES outside those bounds with the range in the body — a clamp would answer a request nobody made and the caller would never learn its date was wrong. There is deliberately **no cap on the number of follow-ups**: `followup_count` is recorded and read by nothing that gates, because the growing intervals are the limit. (3) **Three stops, none of them guessed.** Opted out — read from email-gateway at claim time and their schedule cleared for good; a booked meeting on record — `meeting_booked`, `meeting_attended` or `sale`, live (non-withdrawn) rows of the conversion ledger, hand-stated or tracker-reported, the last two because they entail the booking; answered again — whoever OBSERVES the reply stops the schedule (`kind:"stopped"`, reason stated) and qualification re-decides with a later `kind:"scheduled"`. That third stop is a statement, not a derivation: reply RECENCY is not something this service can see (the delivery layer serves `firstRepliedAt` and no later one), and inventing a heuristic for it would be exactly the fabrication the standing rules refuse. A stop is therefore NOT a tombstone. (4) **Oldest-due-first**, so a burst of fresh replies cannot starve somebody owed an answer since last week. (5) **email-gateway unreachable is a 502, never a claim** — a wasted poll is recoverable, an email to somebody who asked us to stop is not; there is no fallback branch in the claim path at all. (6) **The scope is the campaign id NAMED, not its identity family** — the family rule governs reads that TOTAL a population, while this hands out a single row whose due date a worker wrote naming that exact campaign. `status` is untouched (a served row stays `served`), so the delivery overlay and the read paths' winner ordering are unchanged, and the concurrency guarantee is proven against a REAL Postgres (`tests/integration/followup-queue-sql.test.ts`, eight workers racing one row) because a mocked database cannot fail the way the real one does. **The queue is ENTERED by an email address, not by a row id — `POST /orgs/campaigns/{campaignId}/followups/schedule-by-email`.** It worked and nothing ever seeded it: measured in production, ZERO rows across the fleet carried a due date, so the claim always came back empty and no interested prospect was ever answered. The service that qualifies a reply is the one that knows an answer is owed, and it does not hold `leads_campaigns.id` — it holds the campaign and the person's ADDRESS. So this route resolves that address and writes the same `scheduled` statement the row-id route writes; nothing else about the queue changed. Three things are load-bearing. (1) **Identification is EXACT** (`lookupFollowupRowByEmail`): case-folded equality on the registered `lead_contact_methods` email, scoped to the org and the campaign. The only email→row path that existed was the leads list's free-text SUBSTRING search, which is right for a human scanning results and wrong here — writing the debt onto the wrong row emails somebody who never replied, and that cannot be taken back. (2) **A refusal is NAMED**: unknown is 404 `lead_not_found`, and an address that case-folds onto more than one row is 409 `ambiguous_lead` carrying the matches — never a silent no-op (the caller would believe the debt was recorded) and never a best guess. `idx_lcm_channel_value` makes one email one lead, but it is unique on the value AS STORED, so case is the seam it does not close and ambiguity is real. (3) **The campaign scope is the id NAMED, not its identity family**, exactly as the claim's is: enqueueing onto a sibling would write a debt nothing ever claims. The stops (opted out, a booked meeting on record) are unchanged and still enforced at CLAIM time, which is the only moment they can be read honestly. Nothing is backfilled — only replies arriving after this shipped enqueue, because mailing months-old conversations would answer dead threads.
- **Idempotency is internal.** Use `x-run-id` as the idempotency key. Never expose idempotency keys in the API surface.
