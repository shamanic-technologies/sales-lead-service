# Project: lead-service

**The GitHub repo is `sales-lead-service`; the Hetzner box clones it as `/root/distribute/repos/lead-service`** (container `distribute-lead-service-1`, env `env/lead-service.env`). A deploy poll built on the repo name reads a path that does not exist and looks like a deploy that has not landed.

Apollo/sales lead service: buffering, deduplication, enrichment caching, lead retrieval, lead standing/step statements, read models. Journalist functionality lives in journalists-service.

Module-level rules for the read model, change feed, CRM pairing/evidence, lead history, follow-up queue, paid-pool retry and carried fields live in **`src/lib/CLAUDE.md`** (loaded when you touch `src/lib`). This file holds the service-wide rules.

## Commands

- `npm test` / `npm run test:unit` / `npm run test:integration` (Vitest)
- `npm run build` (tsc + OpenAPI), `npm run dev`, `npm run generate:openapi`
- `npm run db:migrate` applies the journal; `db:push` dev only; **`db:generate` is forbidden** (see Migrations).
- **`generate:openapi` runs in the Docker build with NO database configured**: nothing `src/schemas.ts` imports (transitively) may reach `src/db/index.ts` at import time. v0.82.3 imported `LEAD_STEP_OUTCOMES` from `step-statements.ts` (-> `conversions.ts` -> db) into `step-graph.ts`; the image failed with `LEAD_SERVICE_DATABASE_URL is not set` and `deploy.sh` kept serving the old build. Gate before shipping: `env -u LEAD_SERVICE_DATABASE_URL npm run build`.

## CI never touches a database the service uses

- `.github/workflows/ci.yml` provisions its own `postgres:17` service container; `secrets.*` must not appear in that file on any event (it once migrated the live DSN on `pull_request`). `tests/unit/ci-workflow.test.ts` fails on any `${{ secrets.* }}`. Production migrations come from `migrate()` on boot (`src/index.ts`).
- The CI database is EMPTY: `tests/integration` must seed its own rows. No branch-per-run option exists (Neon is gone).

## The sync back into `staging` is a MERGE commit, never a squash

A hotfix goes to `main`, then a PR whose head IS `main` (`chore: sync vX to staging`) syncs staging: merge it with `--merge`. Squashing (the right default for every other PR here) writes a new commit with content already on main under another sha; the NEXT sync conflicts on byte-identical files. Recovery: branch off `origin/staging`, `git merge origin/main`, resolve EVERY hunk to main's version, confirm `git diff origin/main --stat` is empty. Main is the source of truth; staging is a buffer that deploys nowhere.

## Migrations: hand-author, do NOT `db:generate`

Drizzle snapshots (`drizzle/meta/*_snapshot.json`) stop at `0007`; `0008`+ are hand-authored, so `drizzle-kit generate` would prompt to recreate every table. Hand-write the `.sql` + the `drizzle/meta/_journal.json` entry; make every statement idempotent (`IF EXISTS`/`IF NOT EXISTS`, see `0022`/`0023`). `drizzle-kit migrate` needs no snapshots.

## Architecture

- `src/schemas.ts` Zod schemas (source of truth for validation + OpenAPI); `openapi.json` is generated, never hand-edited
- `src/routes/` handlers (buffer, leads, cursor, health, stats, conversions, won-leads, lead-history...); `src/middleware/auth.ts` API key + multi-tenant headers
- `src/lib/buffer.ts` pullNext()/fillBufferFromSearch(); `dedup.ts` checkDelivered()/markServed(); `email-gateway-client.ts`; `leads-registry.ts` global lead identity (leads + leadEmails)
- `src/lib/people-client.ts` human-service people gateway (provider-agnostic search/enrich). **Do NOT branch on provider in the consumer**: pass every stored identity field (`providerPersonId`, `firstName`/`lastName`/`domain`) and let the gateway pick; `(provider, providerPersonId)` is the disambiguator.
- `src/lib/{campaign,brand}-client.ts`, `runs-client.ts`. **`orgId` is a REQUIRED argument on every `brand-client` read and `x-org-id` always goes on the wire**: a brand row is a shared global identity (same domain = same brand id) and orgs legitimately optimize for different goals; brand-service refuses to guess for a multi-org brand. `buildHeaders` throws on a blank org; never make it optional, never substitute a stand-in org.
- `src/db/schema.ts` (Drizzle), `src/db/index.ts`, `src/config.ts`, `src/instrument.ts` (Sentry), `tests/`

## Data layering and the leads read

- lead-service owns silver `leads`, `lead_contact_methods`, `leads_organizations`, `organizations` and per-campaign lifecycle rows `leads_campaigns`.
- `GET /orgs/leads?view=basic` is a Gold serving projection (slim lead, current-employer summary, primary email, lifecycle fields, live delivery overlay). Prefer a Gold view before a Gold table; never materialize live delivery status.
- **Current employer: never trust a bare `current=true`.** Winner = enriched org first, newest employment row next, stable organization id last.
- **Brand/org scope is ONE row per PERSON** (`DISTINCT ON (lead_id)` global subquery, winner = most advanced lifecycle `served>claimed>buffered>skipped`, then latest `served_at`/`created_at`/`id`; `src/lib/lead-list-query.ts`, used by slim `basicLeadQuery` and full `fetchLeadCampaignChunk`). Campaign scope stays flat. Keyset-paginate over the deduped relation; never `DISTINCT ON` inside a keyset chunk.
- **Each lead carries its ACTIVE audience** (`audience: {id,name,avatarUrl}|null`), resolved server-side before each chunk is written via human-service `POST /internal/audiences/resolve` (direct to `HUMAN_SERVICE_URL`, own 25MB parser; `src/lib/audience-client.ts`). Failure fails loud (500 pre-stream / destroyed socket). Never a browser-side membership fan-out (it 413'd the gateway).
- **Timestamps from raw `sql` are `Date` OR `string`: never `.toISOString()` them; use `toIsoTimestamp` (`src/lib/basic-leads.ts`).** A throw mid-stream destroys the socket (`UND_ERR_SOCKET`). Type raw rows `Date | string | null`; test fixtures use raw strings (`"2026-01-01 00:00:00+00"`).
- **Write-side dual: never bind a raw JS `Date` into a raw `db.execute(sql\`...\`)`; bind `.toISOString()`.** postgres.js Bind throws `ERR_INVALID_ARG_TYPE` client-side, invisible to DB-level tests (it 500'd every `POST /public/conversions` for weeks). Same for a decoded cursor: bind through `leadCursorTimestampParam`.
- **Raw-`sql` route tests that mock `db.execute` do not exercise Bind.** Use the Bind-faithful `assertBindable` mock (`tests/unit/conversions-routes.test.ts`, `lead-list-walk.test.ts`, `leads-route-page.test.ts`) that throws on a `Date`.
- **Bind ANY array into raw `sql` through `sql.param(...)`** (bare arrays compile to `ANY(($1,$2)::text[])`; one element binds as a scalar). **Bind JSON as `${JSON.stringify(x)}::jsonb`, never `sql.json(x)`** (`prepare:false`). A mocked `sql` compiles neither: modules of raw statements need an integration test against real Postgres. Match large key sets with `col = ANY(${ids}::text[])`, never `unnest` joins (nested loop; coalesce nullable columns to false).
- **Identity is EMAIL-FIRST; never serve a lead whose email is unregistered.** `idx_lcm_channel_value` = one email one lead, and the delivery overlay keys on the registered email, so an email-less served lead is invisible to every funnel/cost metric. `upsertLeadFromPerson` resolves (1) lead owning `person.email`, (2) lead with `person.providerPersonId`, (3) new row (provider ids churn, emails do not). `registerServedEmail` fails loud: do NOT restore warn-and-serve-anyway, weaken uniqueness, or read `leads.metadata->>'email'`. Repair: `scripts/repair-served-lead-emails.ts` (`repointed_from_lead_id` records pre-repair attribution).
- **A paid-for, never-contacted serve is un-consumed by ARCHIVING the `leads_campaigns` row into `requeued_serves` and DELETING it, never by flipping status** (`idx_lc_lead_campaign` is unique on `(lead_id, campaign_id)` regardless of status, so a surviving row makes the re-serve's `ON CONFLICT DO NOTHING` keep stale run ids). `scripts/requeue-uncontacted-serves.ts` is the only writer (one-time, `--dry-run`, reversible from `row_snapshot`). Contact evidence comes from the submitting service via two fail-closed gates (`scripts/sql/exclude-vendor-contacted.sql`, then email-gateway `POST /orgs/status` at brand scope). The no-re-serve guarantee is human-service's `brand_suppressions`; lead-service must not write it. Not a recurring sweep (set closed).
- **`timezone` comes from the stored enrichment or stays NULL: never from country/city.** `scripts/backfill-lead-timezone.ts` (one-time, `--dry-run`, idempotent) reads `scripts/sql/apollo-lead-timezones.sql` (plain SELECT on apollo-service's `apollo_people_enrichments`, `COALESCE(time_zone, response_raw->>'time_zone')`), credit-free by construction: apollo-service `POST /enrich` buys on a cache miss. Leads with no city/country keep NULL. Not a recurring sweep.

### Lead list reads: scope, status, bounds

- **A campaign-scoped read answers for the campaign IDENTITY** `(org, brand, offer, leg, channel)` (campaign-service's `uniq_campaigns_org_brand_offer_leg_channel`; unstated offer/leg = `''`), not one stored row: `GET /orgs/leads?campaignId=` and `/orgs/stats?campaignId=` resolve the family (`src/lib/campaign-identity.ts`, `resolveCampaignFamily`, ORG-scoped read of campaign-service `/campaigns`) and filter `campaign_id = ANY(family)`. (1) multi-member scope dedupes per person; (2) delivery evidence keys on the SENDING campaign, so ask in BRAND mode and read members from `byCampaign` (`flattenFamilyStatus`); (3) org-scoped because campaign-service's `brandId` filter matches the legacy `brand_ids` array, and a partial family is worse than none. Resolution failure falls back to the single row with a loud log. Never rewrite stored rows; no opt-in param.
- **Default population is ACTIONABLE: `buffered,claimed,served`, not `skipped`.** `?status=` takes a comma list or `all`; unknown = 400 (`parseLeadStatusFilter`); applied inside the dedup subquery AND the outer query. Do not re-widen the default to fix a consumer: teach it to ask (admin asks `all`).
- **`limit` is honoured; no `limit` still means the WHOLE population** (staff console + features-service read it unpaginated). `limit` + opaque `cursor` (positional twin `offset`), response `nextCursor`; keyset over `(created_at, id)` is a TOTAL order. The bound reaches the DATABASE (`LIMIT/OFFSET` on the outer query), so `limit=50` hydrates 50 rows. No server ceiling. Unparseable bounds (`limit=0`, `abc`, `offset=-1`, foreign cursor, `cursor`+`offset`) are 400, never silent. Route tests must assert the bound reaches the SQL (`tests/unit/lead-list-walk.test.ts`). **The cursor position is `created_at::text` selected as a second column and carried verbatim** (timestamptz has microseconds, JS Date floors to ms: a typed position gave 57,737 rows for 57,622 people). Never build a cursor from the typed `createdAt`.
- **A whole-population figure reads `?view=compact`, and a bounded page is ONE statement that cuts rows BEFORE joining** (scope filter, keyset, LIMIT in an inner subquery; lookups on the page alone; one `.cursor()` statement, not one per chunk; 70s -> 5s on a 49,792-row brand with 0 differing rows). Do not move the cut back to the outer query. `toCompactLead` (`src/lib/compact-lead.ts`, the one serializer) carries the engine's fields read off the SAME row/overlay as `view=basic` (`tests/unit/leads-compact-view.test.ts` asserts field equality), runs no audience/offer/standing resolvers, refuses `include=campaigns` (400), and is gzip-encoded when accepted (gzip scoped to compact only). Do not add fields for non-engine consumers. It states `servedAt`, `lastServedAt` (`COALESCE(retry_claimed_at, served_at)`) and `audienceId` (tagged at serve); never `sent_at`. Migration 0046 re-emits the feed row on re-hand-out. **`crmPositiveReplyAt`** (`src/lib/crm-positive-reply-dates.ts`) is the earliest CRM-evidenced positive reply (`conversion_events` `positive_reply`, `source='crm'`), separate from `replied`/`replyClassification`; a consumer counts a person once when either says positive.
- **A read never holds the population** (count, order, export). The index pass used to build the whole matching set in memory (~3.4 KB/row; 16,599 rows = ~160 MB vs a 384 MB V8 cap): `FATAL heap limit`, exit code 0, restart policy up in seconds, `/health` green, every other org's Leads page down. Rules: (1) the population is WALKED (`streamLeadIndex`, one server-side cursor statement, no array form); (2) ORDER and COUNTS live in the DB, in the scope's read model (`src/lib/CLAUDE.md`); (3) bytes leave as fast as the socket takes them (`src/lib/stream-writer.ts` `ResponseWriter` batches and awaits `drain`, resolves on `close`/`error`). No whole-population array on these paths; no ceiling instead (a silently short file is the bug; an explicit refusal is allowed). Property to re-check: peak memory must not move with result-set size (49,807 records at a 256 MB cap peaked 203 MB). `NODE_OPTIONS=--max-old-space-size=1024` is headroom only.
- **Page/count/search/export are answered HERE.** Additive params, all absent by default (byte-identical when absent): **`total`** beside `nextCursor` whenever a bound or filter is named; **`GET /orgs/leads/bucket-counts`** (counts, no rows; registered BEFORE `/orgs/leads/:id`, reachable through the gateway unchanged); **`?bucket=`**; **`?q=`** (name, title, email, company over the whole matching population); **`?sort=activity`**; **`?format=csv`**. (a) Order/filter depend on email-gateway per-person delivery evidence, so a read naming `q`/`bucket`/`sort` uses the scope's READ MODEL, built from the lean index (`src/lib/lead-index.ts`) and enriched (`lead-engagement.ts`), planned by `lead-page-plan.ts`; the page's own ids hydrate via `rowIds`, an OUTER-only filter that must NEVER move inside the dedup subquery. Order restored in JS from the index. (b) A count and its rows share ONE `resolveLeadReadScope` (offer -> campaigns, campaign -> identity, plus flatten). (c) Buckets are a LENS, not a partition (counts do not sum to `total`; `total` includes people with no evidence). A website visit = measured click OR hand-stated `website_visit`, UNIONED per person (no measured-visit suppression here, unlike `/conversion-counts`). (d) The activity timestamp is never null (outcome, reply, click, open, send, `served_at`, `created_at`) so `(activityAt, id)` is total; compared as an INSTANT; the `created` order is a byte comparison of `created_at::text`; normalize the `created_at` fallback to ISO. (e) Gateway fan-out only when something asks about evidence (100 emails/request, 6 in flight). (f) FAIL LOUD: email-gateway unreachable = 502 (never zeros); unparseable `q`/`bucket`/`sort`/`format` = 400. Search predicates and `uuid[]` hydration are covered by `tests/integration/lead-index-sql.test.ts`.
- **A consumer needing one lead reads it ALONE: `GET /orgs/leads/{id}` -> `{ leadDetail }`** keyed on the list row's `id`, `org_id` in the predicate (foreign = absent), no dedup/lifecycle filter; `brandId`/`campaignId` mean what they mean on the list; a `brandId` the row is not part of is 404. Both routes serialize through the ONE `serializeLeadItem` (`src/routes/leads.ts`; `tests/unit/leads-detail-route.test.ts` asserts the key set). Do not re-solve it as a one-element list filter.
- **The export is headed in the CUSTOMER's words, the JSON is not** (`src/lib/lead-export.ts`): `Yes`/`No`, `YYYY-MM-DD HH:MM:SS` UTC, empty cell not `null`, no internal ids. JSON field names are a contract (features-service, staff console): never "align" the two; no consumer builds its own export. Every column reads the SAME serialized item the JSON emits; a non-timestamp in a date column THROWS.

## Step statements, outcomes, standing

- **A step outcome a HUMAN states counts exactly like a tracked one; a "never" counts nowhere.** `POST /orgs/leads/{id}/step-statements` (org-auth; the publishable tracker token is NOT a door), `{id}` = the `leads_campaigns` row id. `kind:"outcome"` writes a `conversion_events` row `source='manual'` (restating corrects it; signature `m:<leadCampaignId>:<step>`); `bySource` on `/internal/brands/:id/conversion-counts` keeps `tracker + manual (+ crm) === counts`. `kind:"never"` lives in `lead_step_disqualifications` (a table NO count reads: structural guarantee); `GET /internal/brands/:id/step-disqualifications` separates dead from pending. An outcome retracts an earlier never; a never on a step that already happened is 409. **`meeting_attended` and `website_visit` are statable BY HAND ONLY**: `canonicalizeStepOutcome` accepts them, `canonicalizeConversionEvent` (tracker ingest) does not; never widen the tracker vocabulary.
- **`website_visit` is the one step measured BOTH ways: never add the two.** `measuredVisitEventIds` (`src/routes/conversions.ts`) asks email-gateway (brand scope) which hand-stated visits belong to a lead whose click it already measured; every outcome read (`/conversion-counts`, `-by-day`, `/converted-leads`, `/converted-lead-emails`) excludes them, so `counts.website_visit` = visits known only by hand. No hand-stated visit = one indexed SELECT, no network call; no registered email = never suppressed; email-gateway down = 502. `GET /orgs/leads/{id}/step-statements` reads a measured visit as `source:"tracker"` and refuses a `never` on it (409).
- **A statement is a fact about the PERSON at the brand, never the row it was clicked from.** Every read keys on `(brand, lead)` (standing resolver, panel, never guard, withdrawal, implied view, history). The write keeps one statement per `(brand, person, step)`: an outcome takes the signature of any prior manual statement (live or withdrawn); a never updates any prior manual one, both inside one SQL statement (`tests/integration/person-grain-statements-sql.test.ts`). `lead_campaign_id` is attribution only. Never reintroduce `lead_campaign_id = row.id` into a read.
- **Outcomes carrying WHEN and HOW MUCH: `GET /internal/brands/:id/converted-leads?event=<step>`** (date, campaign, `valueCents`, `costCents`, `source`, `causedByOutreach`). Its set is EXACTLY what `/conversion-counts[-by-day]` counts (`outcomes.length` = total); the canonical-email join is LEFT lateral here (INNER on `/converted-lead-emails`, a set of join keys). `campaignId` is null on tracker rows, never guessed.
- **Step order is the LEG GRAPH (`src/lib/step-graph.ts`), never a sales funnel** (retired in wave C3). Legs come from features-service `legKey` (opaque, looked up never parsed). On READ (`src/lib/step-states.ts`): an outcome makes every step all paths to it go through reached (attended => booked); a never closes steps only reachable through it. Sale implies nothing; only a never ON the sale closes it. Precedence per step: own outcome > implied reached > own never > implied closed > pending. Implication is never written; `origin: "stated"|"implied"`; a contradicted never is RETRACTED not deleted (migration 0033, reads filter `retracted_at IS NULL`). `?implied=true` on step-disqualifications applies the graph. `tests/unit/step-vocabulary.test.ts` fails the build if the retired surface (`funnelKey`/`funnelSteps`/`inFunnel`/`stepIndex`) returns to `src`/`openapi.json`, or the banned word for a sales funnel appears (it scans `tests/` too: fixtures included).
- **A closed deal states WHOSE WIN it was: `causedByOutreach`** (migration 0037), optional on any outcome, frozen on the row, three states (`true` ours, `false` theirs, `null` nobody asked: nullable boolean, never `NOT NULL DEFAULT`). A deal we did not cause is REAL: it stays in `counts`, `/converted-leads`, the brand total and `standing: customer`; the flag only lets a consumer exclude its value from OUR outreach return. Not the tracker's `attribution_status` vocabulary (identity matching); never conflate. The list carries `closedDeal` per row (`{occurredAt, valueCents, costCents, causedByOutreach, source}`, `src/lib/closed-deal.ts`), derived on read in the same pass as standing (`createLeadStandingResolver` -> `{standing, closedDeal}`); only a STATED sale answers. Internal reads split `byCause.outreach/.other/.unstated` (sum = counts).
- **Whose win EVERY outcome was follows ONE rule (`src/lib/outcome-cause.ts`, migration 0044):** dated AFTER our first delivered email -> ours; at or before -> not ours; undated / not attributed to a lead / never delivered -> null, NEVER ours. `outcomeCauseRule` is `crmCauseRule` plus a no-lead precondition; no second date comparison anywhere. A person's answer (`stated_caused_by_outreach`) always outranks the rule; worker UPDATEs are guarded on it being NULL; restating without a cause returns to the rule. The reason is stored (`cause_rule`) and served as `causeBasis` (`person`/`rule`/null) + `causeReason`. A worker (`OUTCOME_CAUSE_INTERVAL_MS` 5 min) not a read-time derivation; `never_delivered`/`not_matched` re-evaluated each sweep; email-gateway failing leaves rows unchanged.
- **A step statement can be WITHDRAWN: `DELETE /orgs/leads/{id}/step-statements/{step}`; a withdrawal is the ABSENCE of a statement.** `withdrawn_at`/`withdrawn_by_user_id` (migration 0035); every read filtering `retracted_at IS NULL` also filters it (counts, by-day, converted-*, `/step-costs`, step-disqualifications, panel, measured-visit suppression, contradiction guard). Distinct from `retracted_at`; withdrawing an outcome un-retracts the nevers it retracted (`retracted_by_step = <step> AND withdrawn_at IS NULL`). Re-derivation on read; the response carries `steps` from the SAME `loadStepStates`. Only a PERSON's statement is withdrawable (tracker/CRM/measured = 409 `not_a_statement`; unstated = 409 `nothing_stated` with `state/origin/impliedBy`). Idempotent (`alreadyWithdrawn: true`).
- **A stated `sale` MUST carry `valueCents` (400)**; other steps optional (#450).
- **Every statement MUST state `costCents` (400 `cost_required`), on outcomes AND nevers; that money is the CUSTOMER's and never enters the platform cost ledger** (no runs-service cost, no billing authorize, never in org spend). Absent is a refusal, `0` is a stated zero, `NULL` = nobody asked (legacy rows and tracker events), hence `statedCount`/`unstatedCount` beside totals. Read: `GET /internal/brands/:id/step-costs[?step=]` (one row per live hand statement incl. nevers) and `costCents` on `/converted-leads`. Its set deliberately differs from `/conversion-counts` (MONEY vs POPULATION: a suppressed measured visit is kept here; a retracted never is excluded). Migration 0034.
- **Where a lead STANDS is decided here, per campaign, derived on read: `standing` on `GET /orgs/leads` rows and `/orgs/leads/{id}`** (`src/lib/lead-standing.ts`, pure; commercial policy, once decided in three places: instantly-service#649). (1) LEG-AWARE: `sales_interest` = reached the step the campaign's LEG puts leads on (campaign-service `legKey`, `src/lib/campaign-leg-client.ts`, one org-wide read per response; `entryOfLeg`: `to` of an entry leg, `from` of an internal leg; observed by a CLICK for `website_visit`, a POSITIVE REPLY for `conversation`, nothing for ad-delivered steps). **Exception (owner 2026-09-28): a WEBSITE VISIT is `sales_interest` on EVERY leg** (off-leg: `reachedEntryStep` false, stage `website_visit`, below a disqualifying reply, above a decline). A positive reply on a site leg is `engaged`. No/unknown leg = `unresolved`/`leg_unstated`. `customer` = sale reached; `disqualified` by statement = sale reads never. (2) Precedence is evidence strength; opt-out absolute with its OWN state `opted_out`: unsubscribed > human statement (through `resolveStepStates`) > bounced > entry step reached > reply DISQUALIFICATION > engagement > contacted. A negative reply is NOT a disqualification (disqualified = wrong contact / gone from role, from the provider's derived `disqualified`, optional; absent => `unresolved`/`reply_disqualification_unknown`; `mergeDisqualified` ORs only providers that answered). (3) Nothing fabricated: never served => `not_contacted`; unscoped/unresolvable leg/unreadable statement => `unresolved` + `reason`; a resolver failure downgrades ONE field, never the read. (4) Never stored. (5) Resolved ONCE per response, folding the measured visit from the row's delivery overlay. Do not re-derive in a consumer.
- **The REPLY half is read off EVERY reply's own verdict** (`src/lib/reply-outcome.ts` pure + `reply-verdicts-client.ts`, instantly-service `POST /orgs/reply-verdicts/query`), asked once per chunk by `createLeadStandingResolver`, rolled up at lead x OFFER (a campaign stating no offer is its own grain) and lead x BRAND, served on `standing.replies` (`{offerKey, offer, brand}`). Rules: `latest` = latest REAL reply decides "what now" (machine answers never override a person's; a plain NEUTRAL reply never replaces an interest, only a negative, stop request or hand-over does); `reached` = classification ever reached (`reachedEntryStep` reads it); an opt-out reply is sticky and BRAND-wide -> `opted_out`/`opt_out_reply`; interest and "not our target" per OFFER; referral/off-topic is never interest. Vocabulary NOT copied: read instantly-service's per-verdict flags `automatedAnswer`, `stopRequested`, `notOurTarget`, `handedToPerson` (required; missing = unreadable payload). No reply kind is named anywhere in `src`; `tests/unit/reply-outcome.test.ts` fails if one is. The per-reply layer is the ONLY reply source (hand-recorded = `manual:<id>`, Instantly verdict without mirrored message = `ievt:<event id>`); the coarse delivery `replyClassification`/`disqualified` is never read for standing. FAIL LOUD: unreachable instantly-service / campaign-service unable to say the offer throws `ReplyVerdictsUnavailableError` -> read model 502, list row `unresolved`/`reply_verdicts_unreadable`; never "no replies".
- **A board partitioned by STANDING asks here: `GET /orgs/leads/standing-counts` and `GET /orgs/leads?standing=`.** A standing is a PARTITION (counts sum to `total`), a bucket is a lens; naming both narrows to both. `?standing=` is a comma LIST read as ONE set (`parseLeadStandingFilter`; one order, one `total`, one cursor per column; unknown member or empty set = 400). Same scope resolution, index, overlay and resolver as the list (so a column's size and its rows are the same set); the overlay on `EnrichedLeadIndexRow` is the source, never a second email-gateway call. `unresolved` is COUNTED. FAIL LOUD in both (502 on gateway/standing failure, 400 unknown), unlike the list's per-row degrade. Resolve in `STANDING_RESOLVE_CHUNK_SIZE` chunks. Reachable via the gateway because `/v1/leads/:id` forwards path+query and this route is registered BEFORE `/orgs/leads/:id`.
- **`sales_interest` splits by STAGE: `standing-counts?breakdown=stage` and `?stage=`** (migration 0043, `lead_read_model_rows.stage` = the standing's `deepestStep` else `entryStep`). Absent = byte-identical. `salesInterestStages` lists observed stages, shallowest first on the leg graph, summing to `counts.sales_interest`; `sale` is never a stage; the migration retired every older model; a NULL-stage `sales_interest` row is a 502; the change feed refuses `stage`.
- **`wentCold` is DERIVED, never stated** (`src/lib/lead-cold.ts`; on `standing`, on `GET /orgs/leads/{id}/step-statements`, and `coldCounts/coldByStep/coldLeads` on step-disqualifications). `COLD_AFTER_DAYS` = 30: positive reply (delivery `firstRepliedAt` classified positive, or CRM form reply, earliest) with no meeting booked in 30d -> cold at `meeting_booked`; booked not attended in 30d -> cold at `meeting_attended`; attended or later never cold. (1) Only where the CRM could have SHOWN the step (`crm-cold-eligibility.ts`): contact ever paired, connection not paused, last SUCCESSFUL sync (`lastSyncedAt`) within 6h (a failed attempt with fresh data still applies; past 6h `crm_sync_failing`/`crm_sync_stale`), and a stage meaning serves as evidence; `crm_unreadable` logged, never cached. ## Boot: the port opens BEFORE migrations, traffic gated until they finish

- **`app.listen()` first, `migrate()` behind it.** A database not yet accepting connections (container restart, box reboot, deploy) must not keep the port closed, or `deploy.sh`'s health check rolls the release back for reasons unrelated to the code. No migrations before `listen()`, no pre-listen startup work (`registerProviders()` runs after readiness, non-fatal).
- **`requireBootReady` (`src/middleware/readiness.ts`) 503s every route until migrations complete**; `/health` is mounted BEFORE the gate, everything else after: keep that order.
- **`/health` is boot-state-aware** (`src/lib/boot-state.ts`): `starting` -> 200 `{status:"starting",migrations:"pending"}` with NO DB access; `ready` -> `SELECT 1`; `failed` -> 503 naming the error (deploy rolls back). On migration failure the process stays ALIVE (no `process.exit(1)` restart loop shredding the logs).
- **Migration retry is connect-phase ONLY** (`withConnectRetry`, `src/lib/db-retry.ts`, ~65s, 250ms -> 8s): a rejected connection dispatched nothing; real migration errors are not retried. Transient detection walks `cause` and `AggregateError.errors`, matches driver codes, SQLSTATE class 08, `57P03`, and `timeout exceeded when trying to connect`.
- **Do NOT tune postgres.js connection options for cold starts**: `connect_timeout` already defaults 30, `idle_timeout` defaults null (setting it closes warm connections; brand-service#389 reverted it). Only `net.setDefaultAutoSelectFamilyAttemptTimeout(5_000)` in `src/db/index.ts` is kept.
- **A test that `vi.mock`s `src/db/index.js` MUST `vi.resetModules()` between cases** (else the registry leaks into later files in the worker; `stats-persona-attribution.test.ts` hung because `health.test.ts` ran first). Import the boot-state singleton through the same fresh registry (`tests/unit/health.test.ts`).

## A database connection is never held by a caller who left

- **Pool ceiling and hold times are stated in `src/db/index.ts`, never inherited** (postgres.js default `max: 10` WAS the 2026-09-07 outage: ten whole-population reads took every connection, `/health` 503 for 11.5h, manual restart). `POOL_MAX` (20), `STATEMENT_TIMEOUT_MS`, `IDLE_IN_TRANSACTION_TIMEOUT_MS`: env-overridable, an unreadable override THROWS. They ride the startup packet (session-scoped); never a server-wide `statement_timeout` (shared Postgres).
- **A long read asks between chunks whether anyone is listening: `watchClient` (`src/lib/client-abort.ts`).** Both streaming loops call `client.stopIfGone(rowCount)` at the top of each chunk, before that chunk's fan-out; it THROWS `ClientGoneError` (leaving the generator closes the cursor; a truncated stream must not look complete); route logs `warn` and destroys the socket. Bound on abandonment, not size.
- **`/health` reads its OWN two-connection pool (`healthSql`)**; keep it off the main pool.

## Outbound-call resilience and route errors

- **ALL outbound calls to runs-service go through `fetchWithRetry` (`src/lib/fetch-retry.ts`), never raw `fetch`**: connect-phase retry (`ECONNRESET`/`ECONNREFUSED`, write-safe) + 30s timeout. Any new sibling-service client on a fail-loud path does the same (#390).
- **The serve path's sibling reads stay on `fetchWithRetry` too**: `pullNext` calls campaign-service (`campaign-client`, the campaign's offer) and brand-service (`brand-client.getCurrentGoal`). A connect reset on the offer read drops the offer and brand-service then 409s `SEVERAL_OFFERS` on the goal read (v0.80.1's outage). campaign-client keeps a deliberate **5s** budget shared with the backoff. Retry is connect-phase only; a completed answer (the 409 too) fails loud once. No raw `fetch` in a new serve-path client; do not widen retry to HTTP statuses (#541).
- **A brand-service read scoped to the BRAND is refused on a multi-offer brand** (`SEVERAL_OFFERS`): a dead client pointing at one is a latent copy of that bug (`fetchExtractedFields`/`extractBrandFields` deleted v0.80.2). Name the campaign's offer the way `getCurrentGoal` does, or do not ship the read.
- **Express 4: an `async` handler's throw does NOT become a 500** (unhandled rejection, caller's socket hangs). Every `await` that can throw, including pre-`try` setup (idempotency lookup, in-flight guard, `createRun`), must be inside a `try` that `return res.status(5xx)`s. Tests assert 500-on-throw with NO error middleware (`tests/unit/buffer-route.test.ts`) (#390).

## API design rules

- **Minimal request body**: identity headers workflow-service injects (`x-org-id`, `x-user-id`, `x-run-id`, `x-campaign-id`, `x-brand-id`, `x-workflow-slug`, `x-feature-slug`) are read from headers, never the body.
- **No `.default()` on Zod fields**; a missing field is a 400.
- **No optional convenience fields**: if the service can fetch it (campaign context, brand fields), do not accept it. Extends to headers: a producer-owned attribute derivable from an identified entity is fetched, not required (`goal` from brand-service `runtime-context`, never `x-goal`). Headers that ARE identity (`x-org-id`, `x-campaign-id`, `x-brand-id`, `x-run-id`, `x-audience-id`) stay headers.
- **Audience selection is campaign-owned: lead-service NEVER re-ranks.** `buffer/next` serves the audience in `x-audience-id` (`req.audienceId`); none => clean `found:false`. Do not reintroduce a features-service `persona-stats`/`getTopAudienceId` call (v0.26.1). human-service serve-next 422 "no committed provider" => `found:false` reason `audience_not_serveable`, never 500.
- **Every empty serve NAMES why; exactly ONE name means exhaustion.** `found:false` always carries `reason` (`src/lib/serve-reasons.ts`; the Zod enum reads `SERVE_EMPTY_REASONS`). Only `audience_exhausted` is evidence a population ran out; `no_audience`, `serve_timed_out`, `audience_not_serveable`, `credit_insufficient` are not. A consumer tests `reason === "audience_exhausted"`, never excludes benign values. `no_audience` is reported, never "fixed" by picking an audience here. Cost: campaign `4769db14` asked without `x-audience-id` and was stopped `audience_exhausted` in 1s while its sibling served 109 leads (#439).
- **Idempotency is internal**: `x-run-id` is the key; never expose idempotency keys in the API.
