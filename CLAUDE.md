# Project: lead-service

**The GitHub repo is `sales-lead-service`; the Hetzner box clones it as `/root/distribute/repos/lead-service`** (container `distribute-lead-service-1`, env `env/lead-service.env`). A deploy poll built on the repo name reads a path that does not exist and looks like a deploy that has not landed.

Apollo/sales lead service: buffering, deduplication, enrichment caching, lead retrieval, lead standing/step statements, read models. Journalist functionality lives in journalists-service.

Module-level rules for the read model, change feed, CRM pairing/evidence, lead history, follow-up queue, paid-pool retry and carried fields live in **`src/lib/CLAUDE.md`** (loaded when you touch `src/lib`). This file holds the service-wide rules.

## Commands

- `npm test` / `npm run test:unit` / `npm run test:integration` (Vitest)
- `npm run build` (tsc + OpenAPI), `npm run dev`, `npm run generate:openapi`
- `npm run db:migrate` applies the journal; `db:push` dev only; **`db:generate` is forbidden** (see Migrations).
- **`generate:openapi` runs in the Docker build with NO database configured**: nothing `src/schemas.ts` imports (transitively) may reach `src/db/index.ts` at import time. v0.82.3 imported `LEAD_STEP_OUTCOMES` from `step-statements.ts` (-> `conversions.ts` -> db) into `step-graph.ts`; the image failed with `LEAD_SERVICE_DATABASE_URL is not set` and `deploy.sh` kept serving the old build. Gate before shipping: `env -u LEAD_SERVICE_DATABASE_URL npm run build`.

## CI never touches a database the service uses

- `.github/workflows/ci.yml` provisions its own `postgres:17` service container; `secrets.*` must not appear in that file on any event (it once migrated the live DSN on `pull_request`). `tests/unit/ci-workflow.test.ts` fails on any `${{ secrets.* }}`. Production migrations come from `migrate()` on boot (`src/index.ts`).
- The CI database is EMPTY: `tests/integration` must seed its own rows. No branch-per-run option exists (Neon is gone).

## The sync back into `staging` is a MERGE commit, never a squash

A hotfix goes to `main`, then a PR whose head IS `main` (`chore: sync vX to staging`) syncs staging: merge it with `--merge`. Squashing (the right default for every other PR here) writes a new commit with content already on main under another sha; the NEXT sync conflicts on byte-identical files. Recovery: branch off `origin/staging`, `git merge origin/main`, resolve EVERY hunk to main's version, confirm `git diff origin/main --stat` is empty. Main is the source of truth; staging is a buffer that deploys nowhere.

## Migrations: hand-author, do NOT `db:generate`

Drizzle snapshots (`drizzle/meta/*_snapshot.json`) stop at `0007`; `0008`+ are hand-authored, so `drizzle-kit generate` would prompt to recreate every table. Hand-write the `.sql` + the `drizzle/meta/_journal.json` entry; make every statement idempotent (`IF EXISTS`/`IF NOT EXISTS`, see `0022`/`0023`). `drizzle-kit migrate` needs no snapshots.

## Architecture

- `src/schemas.ts` Zod schemas (source of truth for validation + OpenAPI); `openapi.json` is generated, never hand-edited
- `src/routes/` handlers (buffer, leads, cursor, health, stats, conversions, won-leads, lead-history...); `src/middleware/auth.ts` API key + multi-tenant headers
- `src/lib/buffer.ts` pullNext()/fillBufferFromSearch(); `dedup.ts` checkDelivered()/markServed(); `email-gateway-client.ts`; `leads-registry.ts` global lead identity (leads + leadEmails)
- **A receiver refuses a WHOLE batch on one address it rejects** (email-gateway `/orgs/status`, instantly-service `/orgs/reply-verdicts/query`: `z.string().email()`; crm-service `/orgs/whatsapp/sends/query`: `invalidEmails`). Every batch client drops such an address BEFORE asking via `receiver-email-format.ts` `keepAccepted` (logged `SKIPPED` with lead id, answered as nothing: the receiver can never have acted on it); intake files only `isGatewayEmail` addresses. A NEW batch client sending addresses does the same (LEAD-CHANGES-INVALID-EMAIL-1016: two customer.io unsubscribe addresses 502'd the change feed, then refused filtered lead reads).
- `src/lib/people-client.ts` human-service people gateway (provider-agnostic search/enrich). **Do NOT branch on provider in the consumer**: pass every stored identity field (`providerPersonId`, `firstName`/`lastName`/`domain`) and let the gateway pick; `(provider, providerPersonId)` is the disambiguator.
- `src/lib/{campaign,brand}-client.ts`, `runs-client.ts`. **`orgId` is a REQUIRED argument on every `brand-client` read and `x-org-id` always goes on the wire**: a brand row is a shared global identity (same domain = same brand id) and orgs legitimately optimize for different goals; brand-service refuses to guess for a multi-org brand. `buildHeaders` throws on a blank org; never make it optional, never substitute a stand-in org.
- `src/db/schema.ts` (Drizzle), `src/db/index.ts`, `src/config.ts`, `src/instrument.ts` (Sentry), `tests/`

## Data layering and the leads read

- lead-service owns silver `leads`, `lead_contact_methods`, `leads_organizations`, `organizations` and per-campaign lifecycle rows `leads_campaigns`.
- `GET /orgs/leads?view=basic` is a Gold serving projection (slim lead, current-employer summary, primary email, lifecycle fields, live delivery overlay). Prefer a Gold view before a Gold table; never materialize live delivery status.
- **Current employer: never trust a bare `current=true`.** Winner = enriched org first, newest employment row next, stable organization id last.
- **Brand/org scope is ONE row per PERSON** (`DISTINCT ON (lead_id)` global subquery, winner = most advanced lifecycle `served>claimed>buffered>skipped`, then latest `served_at`/`created_at`/`id`; `src/lib/lead-list-query.ts`, used by slim `basicLeadQuery` and full `fetchLeadCampaignChunk`). Campaign scope stays flat. Keyset-paginate over the deduped relation; never `DISTINCT ON` inside a keyset chunk.
- **Each lead carries its ACTIVE audience** (`audience: {id,name,avatarUrl}|null`), resolved server-side before each chunk is written via human-service `POST /internal/audiences/resolve` (direct to `HUMAN_SERVICE_URL`, own 25MB parser; `src/lib/audience-client.ts`). Failure fails loud (500 pre-stream / destroyed socket). Never a browser-side membership fan-out (it 413'd the gateway). **Each lead also carries `sources`: EVERY audience of the brand that found the person** (human-service `POST /internal/brands/{brandId}/memberships/by-email`, raw, `served` + `found_taken`; asked in parallel with the card, one call per chunk and brand), named by features-service `/public/sourcing-origins` `origins[].audienceLists` (`origin: null` when unnamed, never guessed from audience/cost names; `src/lib/lead-sources.ts`). `audience` stays the serving card. Not on `view=compact`.
- **Timestamps from raw `sql` are `Date` OR `string`: never `.toISOString()` them; use `toIsoTimestamp` (`src/lib/basic-leads.ts`).** A throw mid-stream destroys the socket (`UND_ERR_SOCKET`). Type raw rows `Date | string | null`; test fixtures use raw strings (`"2026-01-01 00:00:00+00"`).
- **Write-side dual: never bind a raw JS `Date` into a raw `db.execute(sql\`...\`)`; bind `.toISOString()`.** postgres.js Bind throws `ERR_INVALID_ARG_TYPE` client-side, invisible to DB-level tests (it 500'd every `POST /public/conversions` for weeks). Same for a decoded cursor: bind through `leadCursorTimestampParam`.
- **Raw-`sql` route tests that mock `db.execute` do not exercise Bind.** Use the Bind-faithful `assertBindable` mock (`tests/unit/conversions-routes.test.ts`, `lead-list-walk.test.ts`, `leads-route-page.test.ts`) that throws on a `Date`.
- **Bind ANY array into raw `sql` through `sql.param(...)`** (bare arrays compile to `ANY(($1,$2)::text[])`; one element binds as a scalar). **Bind JSON as `${JSON.stringify(x)}::jsonb`, never `sql.json(x)`** (`prepare:false`). A mocked `sql` compiles neither: modules of raw statements need an integration test against real Postgres. Match large key sets with `col = ANY(${ids}::text[])`, never `unnest` joins (nested loop; coalesce nullable columns to false).
- **A lead is a HUMAN (human-service) at a COMPANY (brand-service)** (owner 2026-10-13, LEAD-REFONTE-1013; migration 0076). `leads.human_id` = human-service's fleet-view human (a lead row is global, so no org view), `leads.company_id` = brand-service brand id of the current employer (NULL = name-only/no employer, still a lead). "Same human?" is human-service's answer, never decided here; a company's identity facts live in brand-service (written by the sweep from `organizations`, source `lead-service`), never a BUYER fact there (client of X, not our target stay here). Filled by `src/lib/lead-identity-sweep.ts` (background thread: employers 1000/call, facts re-written when `organizations.updated_at` moves, leads 8 resolves in flight); `GET /internal/lead-identity/status` prints the counts. Columns no read-model trigger watches: never add them to a 0042 trigger's column list. Rows serve `humanId`/`companyId` (not on compact). **On the serve** (`serve-identity.ts`, then `upsertLeadFromPerson` with `identity`): a lead owning the address still wins (one email = one lead; served at another company it is logged `identity.address_held_at_other_company`, measured); else the human's lead at THIS company; a provider-id owner at ANOTHER company is NOT reused (job change = new lead, provider id left on the old one). An owner that cannot answer = today's pick + loud log (a paid serve is never stranded); the sweep finishes it. **Company KEY = brand id, else the lead's LOCAL row `leads.organization_id`** (0077: 212k of 256k employers are names only, brand-service never identifies them); "another company" needs two different brand ids, or two different local rows whose names differ too (`isOtherCompany`); a lead moves to the brand id once its row gets one (sweep `adoptResolvedCompanies`). **human-service merges are FOLLOWED** (`human-events.ts`, fleet events only, cursor `human_events`): fleet facts copied to `human_fact_copies`, merges written to `human_aliases` and every lead moved to the canonical human; two leads of one human at one company are RECORDED (`lead_identity_duplicates`, oldest survives for new serves), never physically folded (each lead's delivery evidence is keyed on its own registered email); a split is logged, nothing auto-split.
- **Identity is EMAIL-FIRST; never serve a lead whose email is unregistered** (sole exception: a "Lead follow-up due" serve of a lead the brand already knows by phone alone, `email: null` + `phone`). `idx_lcm_channel_value` = one email one lead, and the delivery overlay keys on the registered email, so an email-less served lead is invisible to every funnel/cost metric. `upsertLeadFromPerson` resolves (1) lead owning `person.email`, (2) lead with `person.providerPersonId`, (3) new row (provider ids churn, emails do not). Before any email, a social engager is held by its social identity, filed as found by the post's campaign (the ONE email-less `served` row, never handed to an email pipe) and merged when served (`src/lib/CLAUDE.md` timeline 6). `registerServedEmail` fails loud: do NOT restore warn-and-serve-anyway, weaken uniqueness, or read `leads.metadata->>'email'`. Repair: `scripts/repair-served-lead-emails.ts` (`repointed_from_lead_id` records pre-repair attribution).
- **A paid-for, never-contacted serve is un-consumed by ARCHIVING the `leads_campaigns` row into `requeued_serves` and DELETING it, never by flipping status** (`idx_lc_lead_campaign` is unique on `(lead_id, campaign_id)` regardless of status, so a surviving row makes the re-serve's `ON CONFLICT DO NOTHING` keep stale run ids). `scripts/requeue-uncontacted-serves.ts` is the only writer (one-time, `--dry-run`, reversible from `row_snapshot`). Contact evidence comes from the submitting service via two fail-closed gates (`scripts/sql/exclude-vendor-contacted.sql`, then email-gateway `POST /orgs/status` at brand scope). The no-re-serve guarantee is human-service's `brand_suppressions`; lead-service must not write it. Not a recurring sweep (set closed).
- **`timezone` has a SOURCE, precedence `stated > enrichment > inferred`** (PUSHED-PERSON-TZ-1014, migration 0082 `timezone_source`/`timezone_basis`/`timezone_checked_at`; `src/lib/lead-timezone.ts` is the only writer, each UPDATE carries its guard). Stated = the client's `timezone` on `leads/by-email` (IANA only, 400 otherwise); enrichment replaces inferred, never stated; inferred (`timezone-inference.ts`, pure) fills an EMPTY zone only, read off lead location > international phone > employer location > email ccTLD: the first signal naming a country fixes it, the zone must be in that country, a multi-clock country without a settling state is NULL (never a guess; NANP/+7 name no country; generic ccTLDs `.io/.co/.ai/.vc`... none). The background sweep visits each zone-less lead once; a filing re-infers. Served as `timezoneSource` beside `timezone`. Never write `leads.timezone` outside that module. `scripts/backfill-lead-timezone.ts` (one-time, enrichment we already bought) predates it.

### Lead list reads: scope, status, bounds

- **A campaign-scoped read answers for the campaign IDENTITY** `(org, brand, offer, leg, channel)` (campaign-service's `uniq_campaigns_org_brand_offer_leg_channel`; unstated offer/leg = `''`), not one stored row: `GET /orgs/leads?campaignId=` and `/orgs/stats?campaignId=` resolve the family (`src/lib/campaign-identity.ts`, `resolveCampaignFamily`, ORG-scoped read of campaign-service `/campaigns`) and filter `campaign_id = ANY(family)`. (1) multi-member scope dedupes per person; (2) delivery evidence keys on the SENDING campaign, so ask in BRAND mode and read members from `byCampaign` (`flattenFamilyStatus`); (3) org-scoped because campaign-service's `brandId` filter matches the legacy `brand_ids` array, and a partial family is worse than none. Resolution failure falls back to the single row with a loud log. Never rewrite stored rows; no opt-in param.
- **`/orgs/stats` outreach figures count PROSPECTS only** (CAMPAIGN-STATS-SENT-ZERO-1018): email-gateway's transactional bucket counts only for recipients who are a lead of the (group's) scope (`prospectTransactional` in `src/routes/stats.ts`, one `groupBy=recipientEmail` call, only when transactional activity exists); a notification to the client's own team stamped with the campaign id (postmark: 0 of 23,086 sends ever carried a `lead_id`) is never a contacted prospect.
- **Default population is ACTIONABLE: `buffered,claimed,served`, not `skipped`.** `?status=` takes a comma list or `all`; unknown = 400 (`parseLeadStatusFilter`); applied inside the dedup subquery AND the outer query. Do not re-widen the default to fix a consumer: teach it to ask (admin asks `all`).
- **`limit` is honoured; no `limit` still means the WHOLE population** (staff console + features-service read it unpaginated). `limit` + opaque `cursor` (positional twin `offset`), response `nextCursor`; keyset over `(created_at, id)` is a TOTAL order. The bound reaches the DATABASE (`LIMIT/OFFSET` on the outer query), so `limit=50` hydrates 50 rows. No server ceiling. Unparseable bounds (`limit=0`, `abc`, `offset=-1`, foreign cursor, `cursor`+`offset`) are 400, never silent. Route tests must assert the bound reaches the SQL (`tests/unit/lead-list-walk.test.ts`). **The cursor position is `created_at::text` selected as a second column and carried verbatim** (timestamptz has microseconds, JS Date floors to ms: a typed position gave 57,737 rows for 57,622 people). Never build a cursor from the typed `createdAt`.
- **Every SERVE of a brand (serve run -> person) is ONE read: `GET /internal/brands/:id/serve-records`** (`src/lib/serve-records.ts`, x-org-id): one row per `leads_campaigns` row carrying `run_id`, every campaign and status, NEVER deduped per person (the list routes dedup brand/identity scope, so features-service walked it campaign by campaign: 2,303 calls, 30 min, 2026-10-08). One streamed statement, no paging, `count` closes the body; identity = `view=basic` projections (unknown name = null, not ""). Do not add paging that re-scans the brand per page.
- **Every source tag of each person, for the SENDING side: `POST /internal/brands/{brandId}/lead-provenance/by-email` `{emails}` (1..1000)** (LEAD-SOURCE-AT-SEND-1016, `src/lib/lead-provenance.ts`; consumer instantly-service ranking sources by bounces/refusals/blocklist hits). x-org-id; one answer per distinct address (case-folded), every address answered: `tags` (sorted: origin slug of each named source, `list:<kind>` unnamed, `list:none`, plus filings `crm_signup`/`social_engagement`/`stated_by_org`), `sources` (= the list's `sources` + `foundAt`), `filings`. MULTI, never the serving source alone. A read: nothing moves who is emailed. human-service or catalogue unreadable = 502, never empty tags.
- **What ONE source pipe found and kept: `GET /orgs/campaigns/{campaignId}/sourcing-stats`** (`src/lib/source-people.ts` pure, `source-people-read.ts` IO; owner 2026-10-11). The source campaign (leg `start_to_lead_found`) names offer + origin; its audiences = the brand's audiences of that offer whose list kind the origin counts (features-service catalogue), NEVER the campaign a serve run was filed under (#712 only). FOUND = human-service memberships (`served`/`found_taken`) + candidates screened here + must-pass declines; KEPT = found AND served to an outreach campaign of the offer; multi provenance (a person counts in EVERY source that found them); unattributable serves are `gaps` counts with a reason. `candidate_screenings.company_domain/name` (migration 0063) recorded at screen time, never backfilled.
- **A whole-population figure reads `?view=compact`, and a bounded page is ONE statement that cuts rows BEFORE joining** (scope filter, keyset, LIMIT in an inner subquery; lookups on the page alone; one `.cursor()` statement, not one per chunk; 70s -> 5s on a 49,792-row brand with 0 differing rows). Do not move the cut back to the outer query. `toCompactLead` (`src/lib/compact-lead.ts`, the one serializer) carries the engine's fields read off the SAME row/overlay as `view=basic` (`tests/unit/leads-compact-view.test.ts` asserts field equality), runs no audience/offer/standing resolvers, refuses `include=campaigns` (400), and is gzip-encoded when accepted (gzip scoped to compact only). Do not add fields for non-engine consumers. `lead.country` is the PERSON's own country (= `lead.country` on basic, null when unknown, never the company's; RESEARCH-COUNTRY-1021, migration 0117 notes its change on the feed). It states `servedAt`, `lastServedAt` (`COALESCE(retry_claimed_at, served_at)`) and `audienceId` (tagged at serve); never `sent_at`. Migration 0046 re-emits the feed row on re-hand-out. **`crmPositiveReplyAt`** (`src/lib/crm-positive-reply-dates.ts`) is the earliest CRM-evidenced positive reply (`conversion_events` `positive_reply`, `source='crm'`), separate from `replied`/`replyClassification`; a consumer counts a person once when either says positive.
- **A read never holds the population** (count, order, export). The index pass used to build the whole matching set in memory (~3.4 KB/row; 16,599 rows = ~160 MB vs a 384 MB V8 cap): `FATAL heap limit`, exit code 0, restart policy up in seconds, `/health` green, every other org's Leads page down. Rules: (1) the population is WALKED (`streamLeadIndex`, one server-side cursor statement, no array form); (2) ORDER and COUNTS live in the DB, in the scope's read model (`src/lib/CLAUDE.md`); (3) bytes leave as fast as the socket takes them (`src/lib/stream-writer.ts` `ResponseWriter` batches and awaits `drain`, resolves on `close`/`error`). No whole-population array on these paths; no ceiling instead (a silently short file is the bug; an explicit refusal is allowed). Property to re-check: peak memory must not move with result-set size (49,807 records at a 256 MB cap peaked 203 MB). `NODE_OPTIONS=--max-old-space-size=1024` is headroom only.
- **Page/count/search/export are answered HERE.** Additive params, all absent by default (byte-identical when absent): **`total`** beside `nextCursor` whenever a bound or filter is named; **`GET /orgs/leads/bucket-counts`** (counts, no rows; registered BEFORE `/orgs/leads/:id`, reachable through the gateway unchanged; also `people: {sent, delivered, interested}`, PEOPLE counts off read-model columns `sent` (an email actually SENT at scope, `isSent`; NEVER `contacted`, which is set when queued in a sequence) and `delivered` (sent AND not scope-bounced, `isDelivered`; never base it on `contacted`: a queued person cannot bounce, so 197 'delivered' showed beside 0 sent) and the UNION of `website_visit`/`positive_reply`, never their sum); **`?bucket=`**; **`?q=`** (name, title, email, company over the whole matching population); **`?sort=activity`**; **`?format=csv`**. (a) Order/filter depend on email-gateway per-person delivery evidence, so a read naming `q`/`bucket`/`sort` uses the scope's READ MODEL, built from the lean index (`src/lib/lead-index.ts`) and enriched (`lead-engagement.ts`), planned by `lead-page-plan.ts`; the page's own ids hydrate via `rowIds`, an OUTER-only filter that must NEVER move inside the dedup subquery (the subquery is narrowed to those ids' PERSONS instead: same winners, 131ms -> 21ms per page; `tests/integration/lead-index-sql.test.ts` fails on the forbidden form). Order restored in JS from the index. (b) A count and its rows share ONE `resolveLeadReadScope` (offer -> campaigns, campaign -> identity, plus flatten). (c) Buckets are a LENS, not a partition (counts do not sum to `total`; `total` includes people with no evidence). **`booking_call`** (owner 2026-10-10, dashboard Outcomes) is an ACT of ours, not an outcome: a person holding an `acted` follow-up ledger row whose acting campaign's campaign-service `legKey` is `conversation_to_booking_call` (AI Instant Call; `src/lib/booking-calls.ts`), never keyed on the row's `source`; no outcome count reads it. A website visit = measured click OR hand-stated `website_visit`, UNIONED per person (no measured-visit suppression here, unlike `/conversion-counts`). (d) The activity timestamp is never null (outcome, reply, click, open, send, `served_at`, `created_at`) so `(activityAt, id)` is total; compared as an INSTANT; the `created` order is a byte comparison of `created_at::text`; normalize the `created_at` fallback to ISO. (e) Gateway fan-out only when something asks about evidence (100 emails/request, 6 in flight). (f) FAIL LOUD: email-gateway unreachable = 502 (never zeros); unparseable `q`/`bucket`/`sort`/`format` = 400. Search predicates and `uuid[]` hydration are covered by `tests/integration/lead-index-sql.test.ts`.
- **A read that names CAMPAIGNS (campaign identity or offer) credits an outcome only when it happened AFTER that scope's FIRST TOUCH of the person** (VALUED-ATTRIBUTION-1014, owner 2026-10-14; `src/lib/campaign-outcome-credit.ts`, applied in `enrichLeadIndex` via `creditsOutcomesAfterReach`): first touch = `campaignFirstTouch`: the scope overlay's `firstSentAt` (email or `withChannelSend`) when it sent, else the row's `served_at` (a source campaign reaches people by finding them; leads-only funnels must credit, one rule, no per-pipe branch); latest instance strictly after it; undated or at-or-before = not credited (bucket, list tab and activity alike). - **A consumer needing one lead reads it ALONE: `GET /orgs/leads/{id}` -> `{ leadDetail }`** keyed on the list row's `id`, `org_id` in the predicate (foreign = absent), no dedup/lifecycle filter; `brandId`/`campaignId` mean what they mean on the list; a `brandId` the row is not part of is 404. Both routes serialize through the ONE `serializeLeadItem` (`src/routes/leads.ts`; `tests/unit/leads-detail-route.test.ts` asserts the key set). Do not re-solve it as a one-element list filter.

## A serve made FOR a pipe only hands out people that pipe can reach, from sources that feed it (owner 2026-10-12)

- **Reach**: `src/lib/channel-reach.ts` reads the outreach channel's contact methods off features-service `/public/sourcing-origins` `contactMethodsByChannel` (WhatsApp/SMS/calls = phone, email channels = email). NO slug list here. Passed as `reachableBy` on serve-next + candidates/next (human-service pushes it to crm-service: an unreachable person is skipped, never marked served) and applied to EVERY pool as `lead_contact_methods` the lead must carry (`reach-sql.ts`: retry pool, source stock, released). A served `person.phone` is recorded as a `phone` contact method. A channel stating no method, or one outside `email|phone` (LinkedIn...), passes nothing (logged once).
- **Sources**: an audience whose origin the channel is NOT fed by (`originsByChannel`) → `OriginNotFedError` → no fresh serve, `found:false reason=origin_not_fed` (it used to be served "keeping the outreach label"); an audience of another offer than the campaign's → `audience_offer_mismatch`. A channel the catalogue names no origins for is unchanged. The campaign's own pools still drain first.
- **Email policy** (`src/lib/email-policy.ts`, CATCHALL-SERVE-OPTION-1013, owner 2026-10-13): `buffer/next` body `acceptedEmails` = `valid_only` (absent: today, nothing on the wire) | `valid_and_catch_all` | `valid_catch_all_and_unknown` (UNKNOWN-EMAILS-OPTION-1014: + verdict unknown, ~15% bounce, owner's knowing choice; owner reaffirmed 2026-10-16 after #953 retired it, UNKNOWN-RESTORE-1016: never deprecate, normalize or refuse it, migration 0100 put back the 12 walk rows 0098 rewrote). ## API design rules

- **Minimal request body**: identity headers workflow-service injects (`x-org-id`, `x-user-id`, `x-run-id`, `x-campaign-id`, `x-brand-id`, `x-workflow-slug`, `x-feature-slug`) are read from headers, never the body.
- **No `.default()` on Zod fields**; a missing field is a 400.
- **No optional convenience fields**: if the service can fetch it (campaign context, brand fields), do not accept it. Extends to headers: a producer-owned attribute derivable from an identified entity is fetched, not required (`goal` from brand-service `runtime-context`, never `x-goal`). Headers that ARE identity (`x-org-id`, `x-campaign-id`, `x-brand-id`, `x-run-id`, `x-audience-id`) stay headers.
- **A serve run is SOURCING, labelled with the audience's sourcing ORIGIN slug, never the outreach slug** (`src/lib/sourcing-origin.ts`: human-service `GET /orgs/audiences/{id}/sourcing-origin`, asked with the OUTREACH slug as `x-feature-slug` because the CRM channel sources from the CRM whatever the provider; an origin features-service `/public/sourcing-origins` `originsByChannel` does not list for that channel would fall out of the channel figures, so that serve keeps the outreach label and logs an error, never a blocked campaign). The `lead-serve` run, `updateRun`, and every downstream call of the serve (`runFeatureSlug` -> `x-feature-slug`) carry the origin; the lead ROW (`leads_campaigns.feature_slug`) keeps the outreach channel (`featureSlug`). Unresolvable = 500 before any run or serve, never the outreach slug. No audience, or an audience serving from no list (422 -> `audience_not_serveable`) = nothing bought, run keeps the outreach slug. Parent link/campaign/audience/brands unchanged.
- **A serve is FILED under the ON SOURCE campaign of the audience's origin** (owner 2026-10-07: an offer's lead sources are campaign-service campaigns keyed offer + origin slug + leg `start_to_lead_found`; `src/lib/source-campaign.ts`, read from campaign-service `GET /internal/campaigns/{outreachId}/source-campaigns`). The serve run (`campaignId`, a child of the outreach run: runs-service accepts a sourcing child's own campaign) and every downstream call (`runCampaignId` -> `x-campaign-id`) carry the source campaign; the lead row, the retry pool and the offer read keep the OUTREACH campaign that works the lead. Rules: channel sources nothing / offer has NO source campaign yet -> today's serve (`legacy`); origin's source campaign ON -> served under it; OFF or absent while the offer has sources -> `found:false` `source_campaign_off`. **No per-campaign ceiling is read here** (owner 2026-10-14, one money model: what a campaign may spend is its SALES FUNNEL caps, which billing enforces at every spend authorization, the serve's purchases included; the old billing `campaign-budget` read and `source_budget_reached` are retired, never re-add a per-campaign ceiling read). Unreadable = 500 before anything is bought. A serve filed under a source is invisible to the runs-service in-flight guard (keyed on the run's campaign), so the outreach campaign's serial invariant is ALSO held in-process (`inFlightOutreach`, `src/routes/buffer.ts`). Person once: human-service's per-brand suppression keys on the person, whichever source found them.
- **LEAD SOURCING** (owner 2026-10-11, `lead-sourcing`: the sourcing channel that picks its origins): when the origin's OWN source campaign is not ON but the offer's Lead Sourcing campaign is, the serve is filed under Lead Sourcing iff human-service CHOSE that origin for the brand (`GET /orgs/lead-sourcing/sources?brandId&offerId`, `chosenOriginSlugs`, asked with the serve's org/user/run; unreadable = the serve fails, nothing bought); not chosen = `source_campaign_off`. Its own ON campaign wins over Lead Sourcing. The serve run carries `lead-sourcing` (the channel it is filed under: its pipe spend reads by its own slug), the origin stays readable off the audience. `sourcing-stats` of a Lead Sourcing campaign counts every list of the origins it may use (`leadSourcing.mayUseByChannel` on features-service `/public/sourcing-origins`).
- **A serve under a source unit is that unit answering its `on_demand` trigger, as its OWN run** (owner 2026-10-11, `src/lib/on-demand-run.ts`): before the serve, campaign-service `POST /internal/on-demand-runs` opens the unit's root run (its campaign, brand, channel, workflow); the `lead-serve` run hangs from it, everything bought under it carries the unit's workflow, and the serve closes it with its own status. A legacy serve (no source unit) is unchanged. Can't open = setup 500 (never a serve whose cost lands on no unit run). **Every answered serve is ONE `on_demand` trigger event at campaign-service** (`lead_requested` before 2026-10-11; `POST /internal/trigger-events`, already `performed`; `src/lib/lead-requested-events.ts`; sourcing legs are REACTIVE on it, campaign-service alerts staff on 3 silent days). Found = `ran` under the serve run's campaign (`runCampaignId`: the ON source, else outreach); empty = `skipped` + the serve's own reason; `requestedByCampaignId` = outreach, idempotency key `on_demand:<x-run-id>` (cache hit and 500 record nothing). NEVER awaited on the serve path: a failed delivery waits in `trigger_event_outbox` (background redelivery, backoff; 400 = `refused_at`, kept), the table is the count of unrecorded asks. Not moved by a brand transfer (transient queue).
- **EVERY PIPE IS INDEPENDENT: a source FINDS in its own runs, the next pipe works its stock** (owner 2026-10-12, LEADS-ONLY-FUNNEL-CAMPAIGN; `src/lib/source-mode.ts`, same door, every origin, no per-channel branch). `buffer/next` with `x-campaign-id` = a source unit (campaign-service row leg `start_to_lead_found`, asked only for a `sourcing-*`/`lead-sourcing` slug) is its OWN run: not ongoing = `source_campaign_off`, then its audiences (`src/lib/source-audiences.ts`: active audiences of brand+offer whose OWN list is that origin, asked with NO channel header (under a CRM channel human-service names EVERY audience CRM: a CRM-contacts unit served Apollo prospects a thank-you-for-signing-up email, LEAK-1012; the released pool asks the same way), or Lead Sourcing's chosen ones; named audience first, then most left to contact), walked until one serves; **WHO the walk finds is the pipe's LEAD STRATEGY, stated by the workflow its play runs: `reachableBy` on the buffer/next body (`email|phone`, all required, added to the channel's own reach via `combineReach`, passed to human-service on every serve of the walk and to every pool)**; **an audience counts for a unit through its own list (header-less `sourcing-origin`) OR an ON SOURCE in its `channels[]` (`sourceId` + `status: active`) whose list kind the unit's origin counts (features-service `audienceLists`), AUDIENCE-SOURCES-1016 (owner 2026-10-16: « the SOURCES should be a concept separate from TARGETING »; a source is never an audience row); the serve goes through it because the run asks human-service under the unit's origin slug; the stock judge accepts a source whatever its on/off now; no source is a CRM list, so LEAK-1012 holds; the released pool still judges the own list only**; a campaign's `audienceIds` is NEVER read (owner 2026-10-14, LEAK-1012: a per-funnel audience pick was rejected and reverted; two strategies of one CRM source never take each other's people); the lead is stored UNDER THE SOURCE (`status_reason='source_found'`), no retry pool, no Bonus check, nobody contacted, no `on_demand` event; `audience_exhausted` only when every audience was walked empty. An outreach campaign fed by a RUNNING source with `runsOnItsOwn: true` (campaign-service, additive; absent = false = today, byte-identical) serves its STOCK (`src/lib/source-stock.ts`: retry pool first, then the oldest unhanded find, claimed `FOR UPDATE SKIP LOCKED` + filed under the outreach campaign in ONE transaction, migration 0068), never finds on demand from it; empty = `source_stock_empty`, no `on_demand` event. **A find is handed only if it STILL fits its audience** (STILL-FITS-1012, owner 2026-10-12: a "never answered" CRM find had answered on WhatsApp by handover and was still messaged): inside the claim's transaction human-service is asked (`src/lib/audience-fit-client.ts`), its verdict never re-graded here, every audience kind alike; no longer fits = row SET ASIDE (`source_set_aside_at` + the owner's reason verbatim, migration 0072), never handed again, next row tried; a person human-service cannot judge (422) is set aside in its words (never fits, never a stock blocked on one row); human-service/crm down or unknown audience = the serve fails, nothing handed or set aside. **A find is handed only if it is the HOLDING source's own** (LEAK-1012 part 2, `src/lib/source-stock-belongs.ts`): audience of the unit's offer, own list = its origin (no channel header); else set aside with that reason, asked before the still-fits question. A stock filled before the rule: `POST /internal/source-campaigns/{id}/stock/recheck` (same judge, per audience, `dryRun` required, before/after counts) and `/stock/adopt {fromSourceCampaignId}` (another source's set-aside, never-handed finds the judge gives this source are re-filed as its own; original row stays set aside). `sourcing-stats` names them: `notKept.no_longer_fits` (+ `noLongerFits` per reason) and `notKept.in_stock` (a find nobody took yet); a find is never a serve there. An audience whose source still answers on demand keeps today's serve. **Leads found per source, fleet: `GET /internal/source-campaigns/leads-found`** (`src/lib/source-leads-found.ts`): campaign-service `ran-counts` (`on_demand` + `lead_requested`) + our `source_found` rows, never twice. **What an earlier run paid to find them: `GET /internal/source-campaigns/reused-acquisitions`** (REUSED-ACQUISITION-COST-1017, owner 2026-10-17 « a lead keeps the price paid to find it »; `src/lib/source-reused-acquisitions.ts`): over the SAME own-run finds (`basis: own_runs`; on-demand finds are filed under the outreach row and bought in the source's serve run, not covered), one apollo-service `POST /internal/acquisition-costs` per org (≤5000/call, finds sent with Apollo person id + first email) -> per campaign `reusedLeads`, `earlierAcquisitionCostInUsdCents`, `paidByOtherOrgsCostInUsdCents` (decimal strings, USD cents). Never re-priced here. An org apollo-service cannot answer (or an answer not covering every find asked) = those campaigns' figures `null` + `unavailableReason`, never 0; the leads-found read never depends on it. Needs `APOLLO_SERVICE_URL`/`APOLLO_SERVICE_API_KEY` (read-only; people are still sourced through human-service).
- **Audience selection is campaign-owned: lead-service NEVER re-ranks an OUTREACH serve.** It serves `x-audience-id`; none => clean `found:false`. The ONE exception is a source unit's own run (above). Do not reintroduce a features-service `persona-stats`/`getTopAudienceId` call (v0.26.1). serve-next 422 "no committed provider" => `audience_not_serveable`, never 500.
- **Every empty serve NAMES why; exactly ONE name means exhaustion.** `found:false` always carries `reason` (`src/lib/serve-reasons.ts`; the Zod enum reads `SERVE_EMPTY_REASONS`). Only `audience_exhausted` is evidence a population ran out; every other (`no_audience`, `serve_timed_out`, `source_stock_empty`, `no_recent_posts`, ...) is not. `no_recent_posts` = human-service answered a linkedin_engagement audience `exhausted` with reason `no_recent_posts` (competitor pages posted nothing in the window); it beats `audience_not_serveable` / `audience_exhausted` in a walk that served nobody (Doc Dinners 8d613bad, 2026-10-13). Cost: campaign `4769db14` asked without `x-audience-id` and was stopped `audience_exhausted` in 1s while its sibling served 109 leads (#439).
- **Idempotency is internal**: `x-run-id` is the key; never expose idempotency keys in the API.
