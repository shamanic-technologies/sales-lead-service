# src/lib module rules (read model, feed, CRM, history, queues, carried fields)

Service-wide rules are in the root `CLAUDE.md`. These govern the modules in this directory.

## The Leads page reads a READ MODEL per scope: `lead-read-model.ts`, migration 0041

Every page read (tab counts, a tab's page, standing counts, a column's page, search) used to rebuild its answer over the WHOLE scope per request (7-9s on the worst brand, 27-30s under the page's five parallel reads; a Won lead took ~30s to appear). Now each scope (brand, campaign identity, offer, statuses...) has one model: a row per person with buckets, standing, activity instant and search text, so a count is `GROUP BY`, a page `ORDER BY ... LIMIT`, a search `ILIKE`.

1. **The derivation is the list's own** (`streamLeadIndex` -> `enrichLeadIndex` -> `attachLeadStandings`, same flatten/resolver/relation); a hydrated page is overlaid from the SAME stored evidence (`readModelDelivery`); a bounded page reads `total` and ids in one REPEATABLE READ snapshot. No second derivation for the model.
2. **Three enforced freshness bounds.** A PERSON's statement is on the VERY NEXT read: triggers on `conversion_events` and `lead_step_disqualifications` write the lead into `lead_read_changes` in the writer's transaction; every read applies new ones first (`catchUp`; "new" = `txid >= applied_xmin`, so a late commit is re-applied; an in-process set of applied seqs avoids recomputing). Evidence another service pushes (`POST /orgs/leads/evidence-changed`: opt-out, classified reply) is re-asked on the next read. Everything else is at most `READ_MODEL_MAX_EVIDENCE_AGE_MS` (5 min) old: a model past it is REBUILT before being read; never serve past the bound on a failed rebuild (502).
3. **Evidence store `lead_delivery_evidence`** (`lead-delivery-evidence.ts`) is keyed like the gateway question `(org, row's PRIMARY brand, '' or single campaign, email)` with WHEN asked; it never decides staleness (each reader names the oldest answer it accepts). An address answered with nothing is stored as NULL result.
4. **The worker (`lead-read-model-worker.ts`, every 15s)** refreshes any model read in the last 7 days once evidence is 3 min old, catches up the rest, PRE-BUILDS the brand model of every brand that served anyone in 30 days, prunes the change log after a day. **A model that exists is refreshed IN PLACE and only rows whose derived value CHANGED are written** (`refreshModelInPlace`, `IS DISTINCT FROM` in `writeRows`); only a first build writes a new model and swaps it in (retired one kept 15 min). Do NOT go back to rebuild-and-swap (it cost 168M inserts + 167M deletes, ~68% of the box's active Postgres backends, for byte-identical rows). Evidence identical to stored is NOT rewritten (`confirmedAt` in-process, valid while `fetched_at` unchanged; compare with allocation-free `sameAnswer` only for re-asked rows; hashing canonical JSON of every stored answer on every read became the largest CPU cost). Do not lower the 3-min cadence without re-measuring. Max two builds at once per thread.
5. **FAIL LOUD**: a model that cannot be built/caught up answers 502; the per-row list standing keeps its degrade-to-unresolved posture.
6. **Every interval sweep runs on the BACKGROUND THREAD (`src/background-worker.ts`), never the request thread**: on the request loop the refreshes (19-58k people per scope, every 3 min) held it long enough that `/health` took 450ms and a 20-row dashboard page 3.5s vs 0.3s idle (2026-10-08). Per-scope serialization therefore crosses threads: `withScopeLock` (`scope-lock.ts`, in-process queue + Postgres advisory lock polled on its own small pool). A refresh holds the scope lock per CHUNK (derive + write), never the whole pass; a read takes it only when a change is pending (`catchUpModel`), and its final leaver-delete spares people a catch-up touched since its xmin. The change feed and the CRM sync use the same helper. Do not start a sweep from `src/index.ts` or reintroduce a scope lock held across a whole refresh.

SQL and freshness are covered against real Postgres (`tests/integration/lead-read-model-sql.test.ts`); route tests use `tests/helpers/fake-lead-read-model.ts` (wiring only, not SQL). After v0.81.11 the page reads spend their time in HYDRATION (audience, offer, standing, campaign cards), not the model: look there first on a regression.

## Change feed for a consumer's copy of compact rows: `GET /orgs/leads/changes`, `lead-change-feed.ts`, migration 0042

features-service keeps a scope's compact rows and fetches only what changed. Per scope (the read model's canonical key) the feed stores each compact row as SERIALIZED TEXT (`toCompactLead`) with the version that last changed it; a leaver becomes a tombstone (null payload, new version). No `since` = whole scope (`full: true`); `since=<cursor>` = rows changed after it plus `removed` ids.

1. **Versions come from the feed row's own counter, bumped in the SAME transaction that writes the rows** (row lock serializes writers), so a plain keyset walk (snapshot by `id`, delta by `version`) never skips a row in flight. Never hand versions out from a global sequence outside that transaction.
2. **What moves a compact row is noted in the writer's transaction** (kind `'lead'` in `lead_read_changes`: triggers on `leads_campaigns` (only columns the row/dedup read, never lease/follow-up/send markers), `leads`, `lead_contact_methods`, `leads_organizations`, `organizations` firmographics via `idx_lo_org`); delivery events arrive as `'evidence'` changes instantly-service already announces; a read applies both before answering. The read model filters to its own two kinds.
3. **Unannounced evidence is caught by a full RECONCILE** re-hashing the scope and versioning only differences: worker every 3 min for a feed read in the last 30 min; a read of a feed whose last reconcile is past 5 min reconciles first (enforced); a read during a worker reconcile answers from what is committed.
4. **A position names its FEED**: a feed unread for a day is dropped; a scope whose campaign identity grew a member is a new key; either way `since` answers the whole scope with `full: true, reason: "feed_replaced"`. That includes an old feed that still exists: a live feed of the same NAMED scope (`sameNamedScope`: org, brand, statuses, queryOrgId, userId, workflowSlug) is `feed_replaced` too (the key hashes what the read resolved, which moves under an unchanged query; prod 2026-09-26 refused features-service its own cursor). A position this endpoint never issued, from a differently-named scope, or past the counter is 400.
5. Page-shaping params (`q`, `bucket`, `standing`, `stage`, `sort`, `format`, `include`, `limit`, `offset`, `cursor`, non-compact `view`) are 400. `tests/integration/lead-change-feed-routes.test.ts` asserts snapshot + every delta == full compact read.

## CRM pairing: which of the customer's CRM people are leads we emailed (`crm-pairing.ts`, `GET /orgs/leads/crm-pairings`)

1. **Pairing is proposed by the SAME identity waterfall that attributes inbound conversions** (`matchConversion`, `conversions.ts`; `MatchResult` gained an additive `candidates` list; attribution path untouched). No second matcher.
2. **A NAME never merges two records**: `signalVerdict` never returns `paired` on a probabilistic tier (email pairs 14 people, first+last name 19, last name alone 164 on the first account). `resolveAttributionStatus` is unchanged.
3. **Where deterministic signals cannot decide, a JUDGMENT does**: typed yes-probability via chat-service `POST /orgs/judgments` (owns model, credential, cost declaration; lead-service declares no LLM cost). FROZEN with the model RELEASE (`jev-1.13.0`, never an alias), never re-asked on read. A judgment the vendor could not produce is `unavailable` with a reason; pairing stays where the signal left it.
4. **A human outranks all**: `crm_pairing_rulings` (migration 0038), precedence human > judgment > signal, keyed on the PAIR (re-running the matcher cannot resurrect a rejection); nothing deleted (withdraw marks `withdrawn_at`; restate clears it).
5. **Their pipeline STAGE names are never mapped onto our steps** (free text per customer): each contact with an opportunity serves `stageNamesComparable: false` + reason; `opportunitiesWithUncomparableStage` measures the gap. The fixed-meaning field is the opportunity's own state, canonicalized to `open|won|lost|abandoned` or `null` (never defaulted to `open`). Their status is a SET.
6. **No read holds the population**: the list is bounded by `limit`/`offset` over THEIR contacts and resolves our half only for the page's paired leads; `GET /orgs/leads/crm-pairing-counts` walks their contacts into O(1) counters, asks no judgment. Both GETs are registered BEFORE `/orgs/leads/:id` (gateway needs no change); the two ruling writes need an api-service proxy. SQL covered by `tests/integration/crm-pairing-store-sql.test.ts` (arrays via `sql.param`).
7. **`?state=` WALKS rather than filters a page** (`walkFiltered`): resolves contacts a chunk at a time via the SAME `resolveContacts`, keeps matches, stops at `limit`. `offset`/`nextOffset` are POSITIONS IN THEIR CONTACT LIST, not ordinals (a ruling moves rows out of the set). Judgments are bought only when the set includes `unconfirmed`; each row is decided after any bought judgment is frozen, so paging a state to the end equals `/crm-pairing-counts` `byState`.
8. `crmContact.record` = their provenance verbatim (type, lead source, tags, created/updated, origin medium/url/referrer; null when absent). crm-service serves company NESTED (`company: {name, website}`): `normalizeCrmContact` (`crm-client.ts`) reads it and the older flat `companyName`, and feeds `company.website` to the matcher's domain tier.

Do NOT write back to their CRM, re-ask a frozen judgment on read, or change what attribution does with the shared matcher. Needs `CRM_SERVICE_URL`/`CRM_SERVICE_API_KEY`.

## CRM evidence on paired leads: `source = 'crm'` (`crm-evidence*.ts`, migration 0040)

crm-service owns what a stage/status MEANS and states each as a dated funnel FACT on its people fact feed; the sync reads them off the bronze copy (`crm-fact-events.ts`: keyed on `crmContactId`, crm's own contact row id = the pairing key; a fact counts until a `withdrawn` fact names it; THROWS, setting nothing aside, until the copy has reached the feed's end once, `crm_feed_cursors.caught_up_at`). `/orgs/gohighlevel/funnel-events` is no longer read. `crm-evidence-worker.ts` (every `CRM_EVIDENCE_SYNC_INTERVAL_MS` = 10 min, plus `POST /orgs/leads/crm-evidence/sync?brandId=`) writes them onto the SAME two stores every step read already reads.

1. **Only `paired`**, decided by the SAME `resolveCrmPairing` (frozen match, judgment, ruling). The pass JUDGES EVERY CANDIDATE first (`judgeEveryCandidate`: matches what was never matched, buys judgments for pairings waiting on one, `MAX_JUDGMENTS_PER_PASS` = 500) via chat-service's PLATFORM twin `/internal/platform-judgments` (worker has no user/run; chat-service declares spend; the view buys org-billed). **Doubt leans to us, visibly**: >= 0.85 pairs, <= 0.15 rejects, between PAIRS with `toConfirm: true` (evidence flows and counts; `GET /orgs/leads/crm-pairings?toConfirm=true`, `pairedToConfirm`). A judgment not produced leaves it `unconfirmed`, re-asked next pass. A ruling triggers `resyncBrand`; a denial withdraws everything it contributed. **A CRM form submitted (step `form_submitted`) is a POSITIVE REPLY**: earliest submission dated strictly AFTER our first delivered email (before/undated/never-delivered is not written), stored as `conversion_events.event='positive_reply'`, `source='crm'`, not a step outcome (the Leads `positive_reply` bucket and the standing read it; `/converted-leads?event=positive_reply` and `/converted-lead-emails` serve it so features-service unions it with email-gateway replies, one person once).
2. **Outcomes** (meeting_booked/attended/sale) are `conversion_events` keyed to the PERSON (`lead_campaign_id` NULL), one per (brand, lead, step) via `crm:<leadId>:<step>`, dated by the EARLIEST dated event (undated only if nothing is dated; `received_at` nullable since 0040). **Nevers** (meeting_not_held -> never attended, deal_lost -> never sale) are `lead_step_disqualifications` `source='crm'` on every campaign row of the person, not written where the step has an outcome. So standing, closed deal, counts (`bySource.crm`), `/converted-leads` and pairings (`ourStanding`, `ourClosedDeal`) move with no consumer change.
3. **A person outranks the CRM, never both count**: stating an outcome sets the CRM row aside (`supersedeCrmOutcome`), the sync keeps it aside while any non-CRM outcome stands, a person's never takes the key over (`source='manual'`), CRM upserts only update rows still `source='crm'`. A CRM row is not withdrawable via the step-statements DELETE (409 `not_a_statement`); correct it by rejecting the pairing.
4. **Whose win**: `crmCauseRule` (see `outcome-cause.ts` in the root rules); `caused_by_outreach` = effective answer, `crm_evidence.rule` = the rule's own. Person override via `GET/PUT/DELETE /orgs/leads/{id}/crm-attribution[/{step}]` (`lead_step_cause_statements`, retractable), read back with `basis: "rule"|"person"`.
5. **Nothing deleted, a failed read sets nothing aside**: stale evidence is `withdrawn_at` at the END of the pass after every sibling read answered (crm-service/email-gateway failure throws first, so a brand is never emptied by a sibling outage).
6. History serves CRM evidence as `type: "conversion"`, `observedBy: "crm"`. Producer note: crm-service records opportunity history only for records that CHANGE on a sync; a connection predating its history table needed a one-time `POST /internal/gohighlevel/rebuild`.

## Lead history: `GET /orgs/leads/{id}/history` (`lead-history.ts` pure, `routes/lead-history.ts` IO)

One ordered answer to "what happened to this person" (previously assembled in the browser from six services). This service holds a lead as a PERSON, so assembly lives here; consumers render without merging.

1. **NOTHING IS RE-DERIVED**: each fact asked of its owner (`outreach-client`, `mailbox-client`, `generated-email-client`); a step statement is carried as stated. An ORDERING, not a second brain.
2. **Asserted is not observed, and the answer says which**: `evidence: "observed"|"asserted"`. A reply whose words we hold is a `message`; one somebody wrote down is a `reply_statement` with no body. `bodyStatus` keeps "held but unreadable" apart from "says nothing".
3. **Scope is stated**: `scope=campaign` (default; whole campaign IDENTITY) or `scope=brand`; the response names the campaigns asked about.
4. **An unreadable source is stated unreachable**: each source has `status`+`reason`, degrades ITSELF and sets `complete: false`; bounded fan-out says `campaignsTruncated` (`MAX_HISTORY_CAMPAIGNS`, six requests in flight). Only our own data being unreadable is a 500.
5. **De-duplication happens here**: a `sent`/`replied` milestone is suppressed when the message carrying those words is listed; **the DRAFTED copy (`generated_email`) is suppressed for a campaign whose outbound message we hold** (still stated for a person nothing was sent to); one message mirrored on outreach and the customer's mailbox is ONE event naming both (`heldBy`), matched on direction, minute, normalized subject, body head.
6. **A `message` carries its LINKS `links: [{text, href}]`** (`message-links.ts`): the sender strips our tracking params from visible text and the provider swaps the destination for its click-tracking redirect. Destinations are indexed off the generated copy this read already fetches (`bodyText`, `bodyHtml`, planned sequence as text), matched on origin+path (host case, leading `www.`, trailing slash = spelling). `href` is only ever a URL WE WROTE (the provider redirect is unreachable by construction; following it would register a click the prospect never made); no match or several parameterizations = `href: null` (never invent tracking params). Additive.
7. **A `clicked` milestone carries `destination: {state, href, resolution}`**: resolved against the copy we wrote to that person on that campaign (the click webhook carries no URL). `ambiguous` (several candidates) vs `unknown` (none) are different facts; `resolution: "deduced"` today (instantly-service holds per-hit URLs in `tracking_hits_raw.payload.url` but does not serve them; wiring `observed` is a producer change, not a relabel). Only on the click milestone.
8. **Nothing depends on the outreach provider being subscribed** (instantly-service reads its own bronze Unibox mirror; the Gmail mirror is sometimes the only copy). Cost per page view: one email-gateway call for the PERSON (campaign evidence read from the breakdown with `flattenCampaignSubsetStatus`, never the brand roll-up), one Gmail-mirror, one recorded-reply, one recorded-opt-out, two per campaign in scope.
9. **A `scheduled` followup carries `answerer`** from campaign-service `POST /internal/campaigns/answerers` (`answerer-client.ts`) for exactly the campaigns holding a scheduled follow-up (the id the claim keys on): `answered` (`answeredBy`), `unanswered` (`absence` verbatim + `startableFeatureSlugs`), `unknown` (`reason`; source `campaigns` `unavailable`, `complete: false`). Nothing here stops/reschedules the debt; a stopped followup has none.
10. **Every generated email names the run that wrote it, `workflowRunId`** (content-generation's own row `runId`, the execute-workflow run, NOT `generationRunId` nor the campaign-trigger parent), on `generated_email` and OUTBOUND outreach `message`; `null` = no readable generation; absent on inbound/mailbox-only/other events.
11. **Staff Gmail** (`staff-mailbox` source, `fetchStaffMailboxConversation` -> google-service `GET /internal/staff-mailboxes/conversation`): staff answer prospects by hand from their own mailbox, mirrored under the STAFF org, so the customer's `mailbox` source never holds it. google-service returns ONLY messages between a staff address (hardcoded `STAFF_ADDRESSES`, byte-equal with the fleet staff allowlists) and this person. `assembleLeadHistory` matches a staff message to outreach's copy WITHOUT direction (instantly labels a Cc'd staff message `inbound`), falling back to sender+minute+subject; a match CORRECTS direction to `outbound`; unmatched = `source: "staff-mailbox"`, `copy: "staff_gmail_mirror"`, `campaignId: null`; unreadable = `unavailable` + `complete: false`.

Env: `INSTANTLY_SERVICE_*`, `GOOGLE_SERVICE_*`, `CONTENT_GENERATION_SERVICE_*`, `CAMPAIGN_SERVICE_*`.

## Paid-pool retry: `pullNext` drains already-paid serves BEFORE asking human-service for anyone new (`retry-pool.ts`, #443)

A serve is billed and suppressed 3 months in human-service immediately, so a failure after it (email generation, vendor push) strands a paid prospect; the suppression is a PRE-payment guard that must not be relaxed. Pool = this campaign's own `status='served'`, `sent_at IS NULL` rows, oldest serve first, `RETRY_CANDIDATE_BATCH_SIZE`, resolved by ONE batched campaign-scoped email-gateway `/orgs/status`.

- **The SENDER's `queued` statement decides first** (broadcast scope): `queued: true` => never re-served whatever its age; `queued` absent => `unknown`, NOT retried, logged loudly (never read as false). Only when the sender holds nothing (`queued: false`): `contacted` false => re-serve now; contacted-not-`sent` => wait, **5-day TTL** from our `served_at`, then re-serve (five not three: Friday-evening queue + bank holiday; stranding is recoverable, a second email to a human is not). Cost of age-only (2026-09-21..24): a backlog past five days made every lead read lost, re-serves hit the vendor's idempotent duplicate and sent nothing (campaign `f7b1b610`: 1,643 attempts over 145 people, new serves ~400/day -> ~50).
- **`finished: true` on the broadcast scope closes a person for good**: `sender_closed_at` (migration 0039), never re-enters the pool. NOT `sent_at` (which history reads as an email that went out); `queued` and `sent` outrank it; absent is never false. (#568: campaign 3922c8e1 handed the same people out 104 times each.)
- `sent` => `sent_at` written, never re-queried (keeps the gateway call small as a campaign ages).
- **Winner by conditional `UPDATE ... RETURNING` on `retry_claimed_at`** (hour-long lease, re-points run ids at the claiming run); lease doubles as queue position. **The claim does NOT write `status='claimed'`**: the overlay and dedup ordering key on `status='served'`, demoting would blank engagement in `GET /orgs/leads`.
- email-gateway unreachable is FAIL-CLOSED: fall through to `serveNext` (costs money) rather than risk a second email. Empty pool = one indexed SELECT. Not a cron/sweep: it belongs on the serve path.

## Follow-up queue: `followup_due_at` + claim lease on `leads_campaigns` (migration 0036, `followup-queue.ts`)

We owe an interested prospect answers at growing intervals indefinitely; the debt is stored per (lead, campaign) and exactly one worker may act on it.

1. **Claim = the same conditional `UPDATE ... RETURNING` as the paid-pool retry**; the lease (an hour) expires. `POST /orgs/campaigns/{campaignId}/followups/claim-next` returns at most one person, exactly once. Concurrency proven by `tests/integration/followup-queue-sql.test.ts` (eight workers racing one row).
2. **The interval is the WORKER's choice, stored, never computed here** (`POST /orgs/leads/{id}/followups`); this service only BOUNDS it (not in the past beyond 5-min skew, not beyond a year) and REFUSES outside with the range in the body (no clamp). **No cap on follow-up count** (`followup_count` gates nothing; growing intervals are the limit).
3. **Three stops, none guessed**: opted out (read from email-gateway at claim time; schedule cleared for good); a booked meeting on record (`meeting_booked`/`meeting_attended`/`sale`, live ledger rows, hand-stated or tracker); answered again (whoever OBSERVES the reply sends `kind:"stopped"` with reason; a later `kind:"scheduled"` re-decides; reply recency is not visible here, no heuristic). A stop is NOT a tombstone.
4. Oldest-due-first. 5. email-gateway unreachable = 502, never a claim (no fallback branch). 6. Scope is the campaign id NAMED, not the identity family (the row's due date was written naming that campaign). `status` untouched.
7. **Entered by email: `POST /orgs/campaigns/{campaignId}/followups/schedule-by-email`** (the qualifying service holds campaign + address, not the row id; it had never been seeded: zero rows fleet-wide). Identification is EXACT (`lookupFollowupRowByEmail`: case-folded equality on registered `lead_contact_methods`, scoped to org+campaign; never the substring search); refusals are named: 404 `lead_not_found`, 409 `ambiguous_lead` with matches (`idx_lcm_channel_value` is unique on the value AS STORED, so case is the seam); campaign scope = the id named. Stops are enforced at CLAIM time. Nothing backfilled (months-old threads are dead).

## Follow-up ledger: `followup_actions` (migration 0045, `followup-actions.ts`), `GET /internal/brands/{brandId}/followup-actions?campaignIds=`

An INTERNAL-leg campaign (ai-meeting-booking) serves no lead of its own; it claims people held by its predecessor leg's campaign (path `campaignId`) and records `acted` on that row, so the queue columns never said whose worker acted. (1) The ledger row is written by the SAME statement as the claim / the `acted` write (data-modifying CTE): no claim without its record, a lost race writes nothing. (2) The acting campaign is `x-campaign-id` (injected from the dispatched campaign); absent = NULL, never guessed from the held campaign. `claimed` and `acted` are served apart. (3) History was READ from Windmill job results (claim-followup/record-followup outputs walked to the root flow's `campaignId`+`runId`, `source='windmill_backfill'`, `source_ref` = job id; retention starts 2026-09-18, first claim that found anybody 2026-09-21 15:22 UTC). One `acted` on row c9324b82 predates the claim evidence and is not attributed. Never attribute by timing.

**What the acting campaign did, for the dashboard: `GET /orgs/leads/conversation-counts?campaignId=<acting>`** (org-auth, gateway `/v1/leads/conversation-counts` via the `/v1/leads/:id` passthrough; registered BEFORE `/orgs/leads/:id`) -> `{campaignId, conversations: {handed, ongoing, meetingsBooked, dropped}}`, PEOPLE since inception. A PARTITION per person (`readConversationCounts` throws if not): booked (live `FOLLOWUP_BOOKED_OUTCOMES` at the brand on a handed row or matched lead) > ongoing (a handed row has `followup_due_at` or a live lease) > dropped (everything else, incl. a requeued/deleted row). Unknown campaign = zeros, never 404. **An acting campaign that never claims (AI Instant Call: instantly-service rings the rep under its own campaign) records its act through `POST /orgs/campaigns/{heldCampaignId}/followup-actions/by-email`** (`recordActedByEmail`: `acted` row, `x-campaign-id` = acting, `x-run-id` required, `source_ref` `run:<runId>` = idempotent; history in migration 0054 keyed on positive evidence, the ring run's revealed Apollo person id). Without it the campaign reads 0.

## Company facts and career history are CARRIED and PERSISTED, never derived here

The email-writing LLM reads the person/company facts the served lead carries; apollo-service holds them (company description 94%, keywords/tech ~100%, founded year 79%, funding stage 21%, full employment list 100%) but they never reached leads, so those prompt variables rendered EMPTY in 87% of generated emails (funding stage 100%). `leads.metadata` does not hold them (Apollo search returns the org object with those keys NULL; only the enrichment has them).

1. **Persisted at WRITE, never derived on read or fetched from a sibling at read time**: `pickOrgFields` (`leads-registry.ts`) copies the widened neutral organization onto `organizations`; `recordEmploymentHistory` writes one `leads_organizations` row per role. Nothing inferred (not from domain/name/industry). A field the producer did not send leaves the column ALONE (absent = null = "nobody stated"; an empty array is not a stated value), so a re-serve never blanks an earlier fill.
2. **Every widened field is OPTIONAL on the wire** (`?` on `PersonOrganization`; the eleven long-standing fields keep their types); `FullLeadSchema` already declared them.
3. **The top-level organization is the CURRENT employer and the only rich one**; past employers are known by NAME (rows key on the name, landing on an existing organization when known). Employment rows match on (organization, start date); a row with NO start date is ADOPTED, not duplicated. Exactly one row is current, enforced not assumed: concurrent titles at one employer ("Founder & Chiropractor") are ONE employment, merged BEFORE writing (row-by-row produced three `current = true` rows); with two current employers the top-level organization wins; with no flag the top-level is current. Nothing deleted.
4. **A role date is a calendar date or nothing** (`normalizeEmploymentDate`): unreadable = role recorded with a null date and a log line.

Backfill: `scripts/backfill-lead-org-enrichment.ts` off `scripts/sql/apollo-lead-org-enrichment.sql` (plain SELECT on `apollo_people_enrichments`; no Apollo API, cannot spend a credit; dry-runnable, idempotent, fills only NULLs, reversible from `--report`). Not a recurring sweep.

## `businessLanguages` is CARRIED, never derived

human-service derives per person the languages they plausibly do business in (ISO 639-1 lowercase, ORDERED most-plausible-first, empty = no signal); content-generation writes each email in the recipient's language. Here we only carry it intact.

- **Never derive/infer/guess a language** (not from city/state/country/name/org); `tests/unit/lead-business-languages.test.ts` guards.
- **Order is the contract** (index 0 = most plausible): `text[]` column; never sort, set-dedupe or normalize.
- **Three distinct states**: `NULL` = predates the field, `{}` = producer had no signal, `{en}` = known English. Never collapse `{}` into `NULL`, never default.
- **Nothing backfilled**; written only via `PERSON_FIELDS` (`leads-registry.ts`; presence IS the write path via `pickPersonFields`). Neutral `Person` (`people-client.ts`) is a pass-through cast; `lead-shape.ts` emits it on single and batch `FullLead` paths.

## `buyingSignal` is CARRIED on the SERVE, never derived

human-service serves nullable `buyingSignal` (`{type: hiring|job_change|funding|linkedin_engagement, occurredOn, fact, source, sourceUrl, engagement?}`; `engagement` = competitor post evidence, linkedin_engagement only, carried verbatim, never email material) for people from a buying-signal audience (apollo-service produces it on reveal), so the cold email can reference it. (1) Lives on `leads_campaigns.buying_signal` (migration 0047), not `leads` (it says why THIS serve surfaced the person). (2) `POST /orgs/buffer/next` hands it out as `lead.buyingSignal` beside `audienceId`; the retry pool hands out the signal stored on the ORIGINAL serve (`loadRetryCandidates`). (3) `readBuyingSignal` (`buying-signal.ts`) is the only reader: absent/null = null; present-but-incomplete THROWS before anything is written. ## Qualification checks: does a lead's COMPANY need the offer? (`qualification*.ts`, `treg-client.ts`, migrations 0051, 0053)

Owner 2026-10-07: human-service says WHO a person is; whether a lead MEETS a business condition is decided here. A criterion = ONE probe from the catalogue (`qualification-probes.ts`) + ONE yes/no question; the AI picks probes, never composes a pipeline, so the price per lead is known up front (`estimate`, read live from treg's catalogue and costs-service, never a hard-coded number).

0. **Criteria belong to the OFFER (brand + offer), cross-audience; no per-audience criteria** (owner 2026-10-07).
